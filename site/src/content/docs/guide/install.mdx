`agent-presence` runs on **macOS and Linux** (Windows is not supported) and needs Node.js 22.13 or newer. Credentials live in Keychain on macOS and libsecret on Linux.

If you use 0.9.0 or earlier, follow [Upgrading](#upgrade-from-090-or-earlier) before replacing the package.

## Agent detection

`setup` detects the six supported agents: `claude-code`, `codex`, `gemini-cli`, `grok`, `opencode` and `pi`. It selects agents reported as `found` or `runnable`. Detection checks only whether commands on `PATH` or agent-owned session/state stores and credential files exist. It does not run agent commands or read credential contents, so detection alone cannot establish `runnable`.

The default agent-owned evidence paths are:

| Agent       | Evidence paths                                                                                                         |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- |
| Claude Code | `~/.claude/projects/`, `~/.claude/.credentials.json`                                                                   |
| Codex       | `~/.codex/sessions/`, `~/.codex/archived_sessions/`, `~/.codex/auth.json`                                              |
| Gemini CLI  | `~/.gemini/tmp/`, `~/.gemini/oauth_creds.json`                                                                         |
| Grok        | `~/.grok/sessions/`, `~/.grok/auth.json`                                                                               |
| opencode    | `~/.local/share/opencode/opencode.db`, `~/.local/share/opencode/storage/message/`, `~/.local/share/opencode/auth.json` |
| Pi          | `~/.pi/agent/sessions/`                                                                                                |

`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GROK_HOME` and `PI_CODING_AGENT_DIR` replace the corresponding default homes. `GEMINI_CLI_HOME` replaces Gemini's parent directory, so its evidence lives under `$GEMINI_CLI_HOME/.gemini/`. opencode uses `$XDG_DATA_HOME/opencode/` when set; detection checks this data home, not its plugin/config home.

An empty session store counts, and retained agent-owned state can establish `found` after the executable is removed. An agent home alone, presence hooks/plugins, shared settings and MCP configuration do not count, so running presence setup does not make an otherwise missing agent detectable.

For a missing agent, setup asks you to install it and run setup again. If a check cannot complete and nothing establishes that the agent is present, setup skips it as `unknown`, names the failed checks and points to `--agents`. A desktop-app-only installation whose CLI has never run and is absent from `PATH` requires this override. You can also use it to limit the selection. It accepts a comma-separated list of supported kit ids:

```bash
agent-presence setup --agents claude-code,codex
```

Unknown ids and kit ids without presence support are errors. Hooks for agents omitted by detection or `--agents` stay unchanged. When the harness ledger has entries owned by `agent-presence` for those agents, setup names them and shows `agent-presence setup --agents <id,...>` to update them. `agent-presence uninstall` removes presence hooks for all agents. Install an agent later and rerun setup to add its hooks. If no agent is detected and `--agents` is absent, setup skips the agent install plan, confirmation, apply and verification. It still prepares the shim for the selected `--hook-command` mode: `package` installs or reuses the pinned runtime, while `absolute` uses the checkout CLI. Only after preparation succeeds does setup continue with the watcher, dsh and provider steps.

`setup` lists configuration conflicts and their allowed resolutions, re-plans with your choices, then shows the complete changes, commands and expected trust prompts. Review and confirm that plan before it writes agent configuration. Canceling, declining confirmation or encountering a protected target stops setup. Login and local home migration may already have written their own data.

In a non-interactive terminal, `setup --yes` applies a conflict-free plan. It does not resolve conflicts automatically. An interactive terminal always asks for confirmation, including with `--yes`. After confirmation, setup installs or reuses the pinned runtime in `package` mode, writes the shim, applies the plan and immediately verifies the kit artifacts selected for this run. If runtime installation fails, it removes the temporary install, discards the plan and exits non-zero before writing the shim or any agent target. If verification fails, setup stops without installing the watcher, offering dsh, publishing to the provider or displaying a signature URL. After successful verification, or when no agent was selected, it installs the macOS power watcher, updates an existing presence dsh plugin or offers a fresh installation, and configures the provider. A canceled dsh prompt or provider failure does not skip the verification results. Linux skips the watcher and relies on TTL pruning.

`--hook-command package` is the default: setup uses npm to install its exact published version into `~/.agent-presence/runtime/<version>/`, then hooks run the installed CLI directly with Node. npm and access to `https://registry.npmjs.org` are needed only when setup installs a missing or invalid runtime; hook execution uses neither npm nor `npx`. `--hook-command npx` remains accepted as an alias for `package`.

To use a local checkout's built CLI without installing a runtime, run:

```bash
node <checkout>/dist/src/cli.js setup --hook-command absolute
```

The default provider is `magic-builder`, so the first `setup` runs the QR login (storing the slot credential) and prompts for a Magic-Builder token. See [Providers](/guide/providers) for the alternative that needs no token.

## Upgrade from 0.10.0

Install this release and run `agent-presence setup`. This installs the pinned runtime and rewrites the shim. The hook commands already installed in agents are unchanged, so no uninstall or additional hook re-trust cycle is needed. dsh and the macOS power watcher also call the shim after setup.

## Upgrade from 0.9.0 or earlier

If setup lists files kept from an earlier removal, first move them out of the install locations, or remove them if unwanted. This includes files installed by this version, such as a modified hook file kept by its uninstall. Do this before any previous-release uninstall, including when replacement entries are also listed. For the remaining old installation, run the previous release's own uninstall before upgrading, without `--credentials` or `--all`. This preserves credentials, configuration and state:

```bash
npx --yes @rivus/agent-presence@<previous-version> uninstall
```

Run the uninstall for each distinct version pinned in replacement hook commands. Also run `0.9.0`, the last release before the harness migration, whenever any replacement entry is not a hook command with a pinned version. Bridge files and opencode config references need this fallback even when other entries pin versions; an older pinned release may not know those later artifacts. For a checkout installation, run `node <checkout>/dist/src/cli.js uninstall` before updating that checkout. Then install this release and run `agent-presence setup` again. Do not use an unpinned uninstall: this version removes only agent artifacts in its harness ledger and leaves previous-release entries outside it untouched. Later upgrades update that ledger in place through setup, without an uninstall.

The previous-release check covers all six supported agents regardless of detection or `--agents`. When setup detects previous-release entries or files kept from an earlier removal, it lists their agent, path and kind, plus the event and command for hooks, and exits non-zero before queue recovery, login or install confirmation. Agent targets and queue files remain unchanged; an approved legacy-home migration can already have run. `--no-hooks` skips this check.

- Entries marked for replacement need the previous release's uninstall above. A renamed plugin copy or hand-edited entry that uninstall leaves must be removed by hand at the listed path.
- Files marked as kept from an earlier removal belong to you, including files installed by this version. Move or remove them by hand; do not use the old uninstall for them, because it would delete your kept file.

This version ignores the old install-target override variables below. Setup names each one that is set, including on a refused run. Keep them set to their original values while running the previous release's uninstall; otherwise its artifacts at those targets remain outside the check:

```text
CLAUDE_SETTINGS_FILE
GEMINI_SETTINGS_FILE
CODEX_HOOKS_FILE
OPENCODE_CONFIG
OPENCODE_AGENT_PRESENCE_PLUGIN_FILE
OPENCODE_AGENT_SIGNATURE_PLUGIN_FILE
PI_SETTINGS_FILE
PI_AGENT_PRESENCE_EXTENSION_FILE
PI_AGENT_PRESENCE_EXTENSION_DIR
```

The check cannot identify an old absolute-path hook command when its checkout path contains no presence marker. The old uninstall normally removes the unquoted form; a quoted checkout path, such as one containing spaces, can escape its matcher too. Inspect the agent configuration and remove any remaining old command by hand, or it can run beside the new hook. `doctor` cannot detect that duplicate either. The old uninstall also removes any Claude, Codex or Gemini hook containing `dist/src/cli.js hook`, including another tool's hook; save and restore those unrelated entries if needed.

The old uninstall also removes the dsh plugin and macOS watcher; setup offers dsh again and reinstalls the watcher. Moving Codex to the stable shim's `hook --agent` command is expected to require one hook re-trust cycle. Later upgrades that only replace the shim keep its installed hook definition stable.

## Installed locations

These are the default user locations for selected agents. The plan shows the resolved paths when an agent home is overridden.

| Agent       | Managed artifact                                                                                                                                                                                                                                                   |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Claude Code | Plugin at `~/.claude/skills/agent-presence/`, with `.claude-plugin/plugin.json` and `hooks/hooks.json`; setup does not add hooks to `~/.claude/settings.json`.                                                                                                     |
| Codex       | With the `codex` CLI available, a marketplace/plugin at `~/.codex/plugins/agent-presence/`, registered through `codex plugin` in `~/.codex/config.toml`; Codex runs its installed cache copy. Without that CLI, hook groups are written to `~/.codex/config.toml`. |
| Gemini CLI  | Extension at `~/.gemini/extensions/agent-presence/`, with `gemini-extension.json` and `hooks/hooks.json`.                                                                                                                                                          |
| Grok        | Its own hook file, `~/.grok/hooks/agent-presence.json`.                                                                                                                                                                                                            |
| opencode    | Bridge at `~/.config/opencode/plugins/agent-presence.js`.                                                                                                                                                                                                          |
| Pi          | Bridge at `~/.pi/agent/extensions/agent-presence.ts`, discovered from the extension directory.                                                                                                                                                                     |

The dsh plugin and macOS power watcher remain presence-managed steps outside the harness bundle. Setup recognizes an already-installed presence dsh plugin by its marker and automatically rewrites it to call the shim, without asking. This also happens with `--yes` or in a non-interactive terminal; it does not depend on accepting a fresh-install prompt. Only a fresh dsh plugin installation requires confirmation, and setup offers it only when dsh is detected in an interactive terminal. The plugin lives at `~/.dsh/plugins/agent-presence.mjs` and is registered in `~/.dsh/cordis.patch.yml`. If setup cannot read the plugin to inspect its marker, it prints one note, skips dsh work and continues provider setup and runtime pruning. `--no-hooks` neither inspects nor rewrites the plugin.

All harness hooks, the dsh plugin and the macOS power watcher call `~/.agent-presence/bin/agent-presence`. Setup atomically replaces this shim. It uses the Node executable from setup, falling back to `node` on `PATH` if that file disappears. In the default `package` mode, the CLI is `~/.agent-presence/runtime/<version>/node_modules/@rivus/agent-presence/dist/src/cli.js`; `absolute` mode uses the checkout's CLI. The agent hook command stays the same in both modes. Absolute mode needs the checkout to remain available.

Setup reuses a runtime whose package version matches and whose CLI exists. After successful setup, cleanup runs under the runtime lock. It keeps this setup's version, the runtime selected by the previous shim before rewriting, and the runtime selected by the shim at cleanup time. This preserves the previous worker's files and the runtime selected by an overlapping setup that finished earlier. It removes only other version directories and leftover `runtime/.install-*` installation directories; directories with other names are preserved. The standalone checkout scripts `install:dsh-plugin` and `install:shutdown-watcher` keep an existing shim or create an absolute-mode shim when none exists.

For command hooks, Claude Code, Codex and Grok receive `timeout: 5` in seconds, while Gemini receives `timeout: 5000` in milliseconds. The opencode/Pi bridges use a 5000 ms child-process timeout only for synchronous finish delivery; other events are sent asynchronously without a child-process timeout. Gemini uses `SessionStart`, `BeforeAgent`, `BeforeTool`, `AfterTool`, `AfterAgent` and `SessionEnd`. Claude's plugin placement avoids adding presence hooks to the settings file Cursor also reads; presence does not install a Cursor source.

Switching existing Codex registrations to the shim's `hook --agent` command is expected to require one hook re-trust cycle. Review the prompts listed in the plan and approve through Codex; setup does not alter trust state. Later updates that only replace the shim keep the installed hook definition stable. Real-agent checks on the 0.11.0 release verified these behaviors: Claude Code 2.1.301 loaded the installed plugin, Codex 0.162.1 reviewed and then ran the plugin's hooks, and Gemini CLI 0.64.0 loaded the extension. Older Gemini CLI versions and the Cursor desktop app are untested.

## Inspect and remove

```bash
agent-presence doctor
agent-presence inventory
agent-presence uninstall
```

`doctor` checks hook health and the harness ledger for all six supported agents, even if they are no longer detected; warnings and errors produce a non-zero exit. Its duplicate checks use both presence-specific previous-release markers and the installed command, and cover command-hook files, not opencode/Pi bridge files. It also checks other tools' hooks, so their warnings can cause exit 1. `inventory` shows the shared kit ledger, including other applications' entries. Both commands accept `--json`; see [Commands](/reference/commands/) for their limits.

`uninstall` covers all six supported agents, including agents no longer detected. It reports removed artifacts and every kept location with its reason, then independently removes the shim, the whole `~/.agent-presence/runtime/` directory, dsh plugin and macOS watcher. It preserves credentials, configuration and session state by default. It removes only harness-recorded agent artifacts; previous-release hooks are not imported into that ledger. Follow the upgrade procedure above to remove them with their own release.
