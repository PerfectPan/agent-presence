## 1. Background and goals

### 1.1 Current behavior and constraints

This repository is a local CLI whose hook command runs inside other agents' lifecycles. The constraints that shape this plan:

- Hooks must stay fast, bounded, non-interactive, and fail-open (`docs/architecture.md`, "Hook runtime"); Codex hooks always print `{}`.
- Presence comes from lifecycle events, never process scans; each agent is a source in `src/sources.default.json` (`builtin:<id>` entries backed by resolvers in `src/cli/hook-context.ts`).
- Credentials never enter config files, hook commands, logs, or signature URLs (`docs/architecture.md`, trust boundaries).

Current hand-rolled implementations and their locations:

- State lock: `withStateLock` creates a `${statePath}.lock` directory, reclaims it by mtime after `staleMs` (10 s), and throws after `waitMs` (2 s) (`withStateLock` and `isStaleLock` in `src/state.ts`). Callers: `src/cli/slot-sync.ts`, `src/cli/deferred-update.ts`, `src/cli/usage-badge.ts`.
- Log lock: `appendRetainedLogLine` guards concurrent appends with a hardlink owner-token lock (`acquireLogLock` in `src/log-retention.ts`, marker `agent-presence-log-retention-v1` in `LOG_LOCK_MARKER`); on `contended` it skips the append, on `unavailable` it appends unlocked.
- Usage: five per-agent scanners (`src/usage/scan-claude.ts`, `scan-codex.ts`, `scan-gemini.ts`, `scan-opencode.ts`, `scan-pi.ts`) feed `collectWindowUsage`, which computes the calendar window `[startOfLocalDay(now) - (days-1)*24h, now)` and scans sources in parallel, fail-soft (`src/usage/index.ts`). Presence's `UsageRecord` (`src/usage/types.ts`) has four separate token buckets where `inputTokens` excludes cache.
- Pricing: `resolvePricing` checks config overrides, then a vendored LiteLLM snapshot, then `DEFAULT_PRICING` (with `mergeOverrides` and `bestPricingKey`, `src/usage/pricing.ts`); `resolveRecordCost` prefers a logged cost, else the bucket formula times the pricing multiplier.
- Hook interpretation: each hook payload is parsed by per-agent resolvers (`src/cli/hook-context.ts`, `src/hooks/claude.ts`), then the event name is mapped through an explicit vocabulary to start/heartbeat/finish, defaulting to heartbeat (`normalizeEvent` in `src/state.ts`); `applyAgentEvent` (`src/state.ts`) owns the state machine (finish, reopen via `UserPromptSubmit`, fallback-finish) and a 3-minute TTL expires sessions.
- Installation: `src/installers.ts` writes hooks into each agent's config by hand — Claude command hooks with `timeout: 5000` (`withClaudeAgentSignatureHooks`, events in `CLAUDE_EVENTS`), Gemini command hooks with Claude's event names and `timeout: 5000` (`withGeminiAgentSignatureHooks`, events in `GEMINI_EVENTS`), an opencode bridge plugin, a Pi bridge extension, and the dsh plugin. `scripts/install-codex-hook.ts` writes Codex hooks for its `EVENTS` with `timeout: 5000` and a `|| echo '{}'` fallback (its `main`). `scripts/install-{claude,codex,gemini}-hook.ts` and the `uninstall-*` variants exist for the isolated-home test flow. The dsh plugin and the macOS shutdown watcher are installed by presence-owned code: setup's dsh opt-in step calls `installDshPlugin` (`src/cli/commands/setup.ts`), and the watcher scripts and the dsh uninstall script are listed in `DEFAULT_SETUP_SCRIPT_NAMES` and `DEFAULT_UNINSTALL_SCRIPT_NAMES` (`src/setup.ts`).
- Command recognition: `isAgentSignatureCommand` matches installed commands by substrings including `agent-presence hook`, `@rivus/agent-presence`, and `dist/src/cli.js hook` (`src/installers.ts`).
- CLI structure: `runCli` statically imports every command (the import list at the top of `src/cli/app.ts`), so a hook invocation loads the installer and setup code too. Claude subagent events get their own session entries keyed `<parentSessionId>:subagent:<agentId>` (`resolveClaudeHookContext` in `src/hooks/claude.ts`).
- Known drift: Claude and Codex hooks get `timeout: 5000` although both agents read seconds (#85); `GEMINI_EVENTS` (`src/installers.ts`) uses Claude's event names (#86); a Cursor agent loads Claude's `settings.json` hooks and maps `PreToolUse` to its own permission hook, where a silent observer blocks (#89).
- Toolchain: the repo pins `minimumReleaseAge: 1440` with `minimumReleaseAgeStrict: true` (`pnpm-workspace.yaml:11-13`), and `engines.node` is `>=22.13` since batch 4 (`package.json:62-64`). The kit publishes `@rivus/agent-kit` and `@rivus/agent-kit-collab` — 0.11.0 (published 2026-10-11) — with `engines: >=22.13` and an exact optional peer `effect@4.0.1` (kit `packages/agent-kit/package.json`). The kit source files this plan cites are unchanged between v0.7.0 and v0.11.0 except `docs/development/adoption.md`, which gained the runtime-boundary sentence this plan cites (`/node` and `@rivus/agent-kit-collab/process-lock` bundle `zod/mini`) and a session-viewer step it does not cite. v0.12.0 changes the cited files only in types, comments, an equivalent payload-reading refactor (with a new test), and wording (adoption.md's "host" becomes "per-agent"), so citations stay pinned to v0.11.0 (checked with `git diff --stat` over the cited paths); each batch pins the latest kit release at implementation time and re-verifies its citations against it. The latest release, kit 0.13.0 (published 2026-10-13), which batch 4 pins, changes the opencode dialect and bridge (agent-kit#86, agent-kit#99) and the adoption guide's hook step to match; the citations of that opencode behavior point at v0.13.0.

The kit's own migration guide for this repository is [docs/development/adoption.md](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/docs/development/adoption.md) in the [agent-kit](https://github.com/PerfectPan/agent-kit) repository; its "Public entry inventory", "Presence", "Verification and rollback", and "Known limits" sections are the source of several decisions below. Kit source paths in this document are relative to that repository.

### 1.2 Problem

Presence duplicates, and has already drifted from, what the kit now ships: per-agent hook vocabularies (#86), timeout units (#85), permission-gate semantics (#89), usage transcript decoding, pricing, install/uninstall flows, and process locks. Every new agent or decoding fix currently means hand-maintaining all of it here. The kit ships these as versioned, tested entries; adopting them removes the duplication and fixes #85/#86/#89 in the same motion.

### 1.3 Goals and success criteria

- Spec 0002 scenarios S1-S13 pass, each mapped to a batch and test in section 6.
- The five hand-rolled usage scanners, the hand-rolled pricing resolution, the hand-rolled hook/config installers for kit-covered agents, and both hand-rolled locks are deleted and replaced by kit entries (the deleted-modules list in issue #92).
- The hook entry's import graph contains no `effect` and no setup code, and the hook cold start does not get slower.
- `dist/src/cli.js hook` keeps working as the installed hook command (its generic fragment is no longer a legacy marker — 3.5 records the consequences).
- Install, verify, doctor, uninstall, and the documented downgrade pass under an isolated `HOME` for every kit-covered agent.
- No credentials or private paths enter config files, hook commands, ledger contents, logs, or this repository.

### 1.4 Non-goals

- A Cursor source (the kit ships no Cursor usage decoder; see 3.6).
- A blocked presence status driven by the kit's blocked lifecycle phase (presence keeps three statuses).
- New agents beyond Grok.
- Toolchain changes (lint-config v0.6.0, the Vite+ build) — delivered separately per issue #92's ordering; this plan only consumes them.

## 2. Outline

### 2.1 Design principles

- One kit area per PR, in dependency order, each with old-behavior and new-behavior evidence (kit adoption doc, "Verification and rollback").
- The kit owns agent semantics: which events exist, what they mean, where hooks install, how transcripts decode. Presence owns its product policy: source ids, the state machine, TTL, rendering, providers.
- A kit gap is fixed in the kit and released first, never worked around in presence (kit adoption doc, "Known limits").
- Unknown data (hook payloads, state and record files, configuration) is read through kit readers or parsed once at the boundary with zod/mini; no hand-written shape guards. Presence has no zod dependency today (batch 4 landed without one). The first change that parses unknown data with a schema adds `zod` at the range the kit's packages declare (`^4.6.5` in 0.13.0), so the lockfile resolves one zod copy: batch 2, which parses the pricing snapshot and the `usage.pricing` overrides it feeds to `createPricing` (3.2), or [Plan 0003](0003-hook-event-queue.md)'s Q1a, which parses queue records and its two state fields, whichever lands first.
- The hook path never imports Effect or setup code; the single `Effect.runPromiseExit` lives at the CLI root for setup-shaped commands.

### 2.2 Boundaries and responsibilities

| Area         | Kit owns                                                                                  | Presence owns                                                                  |
| ------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Process lock | `acquireProcessLock` mechanics (SQLite exclusive lock, file fallback, holder diagnostics) | Which paths are locked and the wait/skip policy per call site                  |
| Usage        | Transcript decoding per agent, dedup                                                      | Windows, per-source snapshots, badges, dsh usage events                        |
| Pricing      | Price tables, LiteLLM conversion, cost formula                                            | Snapshot refresh, config overrides, fallback table, badge rendering            |
| Hook events  | Payload → lifecycle interpretation, dialect rules (timeouts, output, gates)               | Source ids, session identity, presence state machine, TTL/reopen               |
| Install      | Placement strategies, ledger, plan/apply/verify/doctor/inventory/uninstall                | Bundle definition, setup UX, dsh plugin, shutdown watcher, provider publishing |

### 2.3 Main path

After all batches: a hook invocation resolves the presence source from `--agent {agent}`, interprets the payload with `readHookEvent` (`@rivus/agent-kit/harness/events`), feeds the phase through the presence-owned signal mapping into the unchanged presence state machine under the state lock now provided by `acquireProcessLock`, and rescans the usage window with `scanUsage` (`@rivus/agent-kit/transcript/usage`), replacing that window's per-source snapshots priced through `@rivus/agent-kit/cost`. `setup` builds a kit `Bundle`, shows the plan from `planInstall`, applies it, and verifies; `doctor`, `inventory`, and `uninstall` are kit-backed CLI commands. The hook command import graph contains neither `effect` nor setup code.

## 3. Detailed design

### 3.1 Process lock

**Plan 0003 takes this off the hook path.** The owner chose option (c) of the hook-path lock cost decision (Owner decisions, 2026-10-13): [Plan 0003](0003-hook-event-queue.md)'s Q1 replaces batch 1 and implements this section: the hook records its event and returns without a lock or a log line, so the state lock and the log lock below run only in Plan 0003's worker and in the CLI commands, and the kit lock also becomes the worker's single-instance lock. Q1 replaces both locks as described here, the hardlink log lock included, so the deletion list (6.2) and Spec 0002's lock requirement stand; the one change is that the worker's dsh usage append waits until it holds the log lock instead of skipping after the bounded wait, because it runs off the hook path and must not lose usage; a handover interrupts the wait and the append stays owed (Plan 0003 3.5).

**Chosen approach.** Replace `withStateLock`'s mkdir implementation with the kit's `acquireProcessLock(platform, path, options)` from `@rivus/agent-kit-collab/process-lock` ([source](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/agent-kit-collab/src/process-lock/application/use-cases/acquire-process-lock.ts)): with `platform.sqlite` present, `path` is a SQLite database held in `locking_mode=EXCLUSIVE`, so the kernel releases the lock when the process exits or crashes; a `.holder` file next to it records the holder for diagnostics. Without SQLite the kit falls back to an identity-bearing lock file with dead-holder reclamation. The platform comes from `createNodePlatform()` (`@rivus/agent-kit/node`).

- The lock target moves to a new path, `${statePath}.lock.db` — never the state JSON itself (the SQLite mechanism turns `path` into a database), and never the old `${statePath}.lock`: the previous version deletes that path on release and on stale reclaim (the `rm(lockPath, ...)` calls in `withStateLock`, `src/state.ts`), so a database living there would be deleted under a live holder during an upgrade overlap, and a third process could then lock a fresh file at that path. The old lock directory is left alone (no pre-clean); with distinct paths, neither version deletes the other's lock.
- `withStateLock(statePath, fn, { waitMs })` keeps its signature so its callers (`src/cli/slot-sync.ts`, `src/cli/deferred-update.ts`, `src/cli/usage-badge.ts`) do not change; internally it calls `acquireProcessLock` with `wait: true` and `signal: AbortSignal.timeout(waitMs)` — the kit's `wait` flag has no built-in budget, so the deadline is the signal — and maps an abort to the same timeout error it throws today. The parent directory is created before acquiring (the kit requires an existing directory). The mkdir/stale-mtime code (`withStateLock`'s mkdir loop and `isStaleLock` in `src/state.ts`) is deleted.
- Log retention: `acquireLogLock` (`src/log-retention.ts`) is replaced by `acquireProcessLock` with `wait: true` and `signal: AbortSignal.timeout(LOG_LOCK_WAIT_ATTEMPTS * LOG_LOCK_RETRY_MS)` — today's bounded wait, 250 attempts × 10 ms ≈ 2.5 s (`acquireLogLock`'s retry loop over those two constants). A timeout or `ProcessLockHeld` maps to today's `contended` (skip the append) and an unexpected acquire failure keeps today's `unavailable` (append unlocked) fail-open behavior. The hardlink code and the `agent-presence-log-retention-v1` marker are deleted. The lock change uses only plain kit entries, so it adds no `effect` dependency (the exact pin lands with `/harness` in 3.5).

**Rejected alternative.** Keep the mkdir lock and only fix its edge cases (stale-mtime races, cross-platform `link()` gaps): rejected because crash-safety is exactly what the kit's kernel-released SQLite lock provides and presence cannot match it without reimplementing it — this is the kit area the adoption starts with per issue #92.

**Kit entries used.** `@rivus/agent-kit-collab/process-lock` (`acquireProcessLock`, `ProcessLock`, `ProcessLockHeld`), `@rivus/agent-kit/node` (`createNodePlatform`).

**Stays in presence.** Which paths are locked, wait/skip policy, all state and log logic.

**Compatibility.** `engines.node` is already `>=22.13`, the kit Node adapters' floor: batch 4 raised it (`package.json:62-64`). Mixed-version overlap: an upgrade uninstalls the previous release before the new release's `setup` (Plan 0003 3.12, decided by the owner), so a previous-version hook (mkdir lock at `${statePath}.lock`) and this version's worker and commands (SQLite lock at `${statePath}.lock.db`) are not meant to run together; if they do, they do not exclude each other — different paths and primitives — though neither deletes the other's lock (7). A holder that is alive but stuck now makes waiters time out after `waitMs` (2 s) instead of being reclaimed after 10 seconds of mtime staleness; the crashed-holder case improves from timed reclaim to immediate kernel release.

### 3.2 Usage and pricing

**Chosen approach.** Replace the five scanners with one stateless `scanUsage(platform, { agents, since, until })` call per window ([source](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/application/use-cases/scan-usage.ts)) — no persisted `UsageScanState`, as the owner decided (Owner decisions, usage scan state); issue #92 step 1 and the kit adoption guide say the same since that decision ([agent-kit#104](https://github.com/PerfectPan/agent-kit/pull/104)). Every scan re-reads the whole window from `since: <window start>`, prices the emitted records with the current pricing, and replaces that window's per-source snapshots exactly as `collectWindowUsage` and the badge cache do today (`src/usage/index.ts`, `src/cli/usage-badge.ts`). This is the cost model presence already has — it rescans every window today. It keeps windows independent, makes overlapping scans idempotent (two scans of one window produce the same snapshot), and applies price changes on the next scan. `scanUsage` returns an async iterable of `UsageRecord | UsageDecodeFailure | UsageSourceFailure`; the record carries `usage` (kit convention: `inputTokens` includes cache reads and writes, `outputTokens` includes reasoning — [usage.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/value-objects/usage.ts)), optional `costUsd`, and optional `pricingMultiplier`.

- **Source selection stays table-driven.** `collectWindowUsage` keeps its window math (`src/usage/index.ts`) and resolves sources through `billableSources` (`src/sources.ts`): `enabled: false`, config-overridden entries, custom handler sources, and table order keep today's semantics. Built-in sources with kit decoders map to kit agent ids and are batched into one `scanUsage` call per window; a custom handler source keeps its handler scanner, and dsh keeps its own scanner, merged at the totals boundary. A same-day hook refresh scans only the boundary's owning source (`refreshUsageBadgeCache` in `src/cli/usage-badge.ts`), as today. The `includeHandlers: false` trust boundary is untouched.
- **Totals mapping (badge parity).** Presence's old four-bucket total equals `usage.inputTokens + usage.outputTokens` (kit input includes cache). Badges keep rendering `totalTokens` + `$cost`, so S7's token totals are identical by construction. Cost: `priceUsage` ([price-usage.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/cost/src/domain/pricing/services/price-usage.ts)) uses the same term order as presence's `resolveRecordCost` (`src/usage/pricing.ts`) — logged cost wins unmultiplied, token cost times the record's multiplier — so dollars agree.
- **Pricing table.** `createPricing(table, { overrides, fallback })` from `@rivus/agent-kit/cost` replaces `resolvePricing`'s merged-table lookup (`src/usage/pricing.ts`). The snapshot is injected directly: its `prices` entries are already per-million `input`/`output`/`cacheWrite`/`cacheWrite1h`/`cacheRead` (`src/usage/litellm-pricing.json`), which is `createPricing`'s form. `fromLiteLLM` ([from-litellm.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/cost/src/domain/pricing/adapters/from-litellm.ts)) is not applied to the snapshot — it expects raw LiteLLM entries with `input_cost_per_token`/`output_cost_per_token` and would produce an empty table for this snapshot, silently degrading prices (claude-opus-4-8 would fall back from its snapshot input price to the broad opus price). If used at all, `fromLiteLLM` belongs where raw LiteLLM data enters — the snapshot refresh. Presence keeps: snapshot storage/refresh, `usage.pricing` config overrides (passed as `overrides`), and `DEFAULT_PRICING` as `fallback`. The snapshot file and the `usage.pricing` overrides are parsed once with a zod/mini schema where they enter `createPricing` (2.1). Unknown models still render tokens with n/a cost (`UsageTotals.costUsd` absent).
- **Trailing-request lag (behavior change, per decoder; applies to stateless scans too).** Finalization is per decoder, not one uniform rule, and none of it depends on scan state: the Claude Code decoder withholds a request while it is among the four most recent in its conversation lane (`OPEN_PER_LANE = 4`, released at `lane.open.length > OPEN_PER_LANE`, [claude-code.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/claude-code.ts)) — a withheld request is released once four newer requests have been written in its lane, never by a single later request (a lane holding one open request stays withheld when a second is written) — or until the source is decoded with `final`, which `scanUsage` does once the source has been quiet for 30 minutes ([scan-usage.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/application/use-cases/scan-usage.ts)); the opencode decoder returns `"running"` for a message in the SQLite database without `time.completed` (which opencode sets when the message ends, also on error or abort) and counts it only once completed or the source is finalized ([usage.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/opencode/usage.ts)), while a message in the legacy `storage/message` JSON store always carries a settle time and counts immediately ([usage-decoders/opencode.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/application/services/usage-decoders/opencode.ts)); the Gemini CLI, Pi, and Codex decoders emit a request's usage as soon as its record is complete, without waiting for quiet ([gemini-cli.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/gemini-cli.ts), [pi.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/pi.ts), [codex.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/codex.ts)). After adoption, snapshots and badges leave out a still-active Claude Code source's newest requests (up to four per lane) and an opencode source's still-running database messages, while Gemini/Pi/Codex trailing requests count as today. Presence today counts every record it reads immediately (`scanClaude` in `src/usage/scan-claude.ts`). The owner accepted each decoder's finalization (Owner decisions, usage trailing-request policy): presence does not work around it, and batch 2 documents the lag per decoder in `docs/architecture.md`'s usage section and the token-usage guide.
- **Grok.** Batch 2 wires Grok's kit-backed usage decoding (kit agent id `grok` batched into the `scanUsage` call), and batch 4 adds the `builtin:grok` source entry (`src/sources.default.json`) together with its hook resolver (3.4) — the source entry has to exist before Grok lifecycle or usage is observable, and `resolveHookContextForSource` resolves nothing for an absent entry (`src/sources.ts`), so no Grok presence or usage change is observable until batch 4 (no hooks install until 3.5). Presence source id `grok` equals the kit agent id.
- **Corrections adopted** (each cited, each fixture-tested, per the adoption doc's "do not hide decoding corrections in a broad tolerance"):
  - Codex per-record tier: the kit reads each record's own `serviceTier` and applies `codexPricingMultiplier` per record ([codex.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/codex.ts)); presence applied the current `~/.codex/config.toml` tier to every record in the window (`scanCodex` reads it once through `readConfiguredPricingMultiplier`, `src/usage/scan-codex.ts`).
  - Gemini migrated chats counted once: only the `.jsonl` file of a migrated chat is a source ([gemini-cli.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/application/services/usage-decoders/gemini-cli.ts)).
  - Claude dedup per request: the kit keys a turn by `requestId`, falling back to the message id when a gateway recorded none ([claude-code.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/claude-code.ts)); within a request it keeps the copy with the larger token total, preferring the later copy only on ties (`claudeCodeRequestUsage`, the same keep-largest rule as presence's `scanClaude`), and the window counts a key at its first emission across files; presence keyed `${message.id}:${requestId}` (`dedupKey` in `extractRecord`, `src/usage/scan-claude.ts`). Synthetic turns stay excluded (both sides).
  - Gemini tool tokens counted: a record's input tokens become `input + (tool ?? 0)` ([gemini-cli.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/gemini-cli.ts)), where `src/usage/scan-gemini.ts` omits tool tokens.
  - Pi forked-session parent entries skipped: usage entries copied from the parent session are not counted again ([pi.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/pi.ts)), where `src/usage/scan-pi.ts` counts them.
  - Codex `token_usage_record` precedence: from its first sight of a record the decoder switches to per-record usage and skips unchanged `token_count` totals ([codex.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/domain/usage/adapters/codex.ts)), which `src/usage/scan-codex.ts` handles neither way.
  - Absent-versus-zero: counts a transcript does not report stay absent instead of 0.
  - opencode store and fallback: the kit reads the SQLite message store and uses the legacy `storage/message` session directories only when no database exists ([opencode.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/sessions/src/application/services/usage-decoders/opencode.ts)) — the legacy fallback itself is not a kit gap. The real difference: when `opencode.db` exists but cannot be read, the kit reports a source failure while presence falls back to legacy JSON (`docs/architecture.md` usage section). Current opencode (1.18.11) keeps sessions in `opencode.db` (`storage/` holds only `migration` and `session_diff`), so the fallback difference is the fixture-tested edge — see 3.6.

**Rejected alternatives.** (a) Keep presence's scanners and only port individual fixes: rejected — every future agent/decoding fix would stay hand-rolled, which is the problem. (b) Let the kit own windows and badges too: rejected — presence's per-source snapshot and aggregate rules (`refreshUsageBadgeCache` and `aggregateSnapshots` in `src/cli/usage-badge.ts`) are product policy the kit does not ship, and moving them would break the downgrade story for no kit benefit. (c) Persist the kit's `UsageScanState` cursors and store incremental deltas (per-day buckets): rejected by the owner's decision (Owner decisions, usage scan state) — the persisted cursors partition the window, so a scan reads only what was written since its cursor and a second scan of a quiet window yields nothing; overlapping scans then double count or drop the first scan's usage — atomic cursor and aggregate commits alone do not cure that, because two readers of the same cursor still need serialization or revision checks; price changes apply only to not-yet-counted records, leaving stale prices in stored buckets; and each window rollover must decide between subtracting an expired contribution from a live aggregate or re-deriving it. The stateless rescan has none of these modes and matches the cost model presence already has.

**Kit entries used.** `@rivus/agent-kit/transcript/usage` (`scanUsage`, `decodeUsage`, `UsageRecord`, failure item types), `@rivus/agent-kit/cost` (`createPricing`, `fromLiteLLM`, `priceUsage` via `costOf`, `summarize`, `calendarWindow` if needed for self-checks), `@rivus/agent-kit/node` (platform).

**Stays in presence.** dsh usage events (host-owned protocol), windows, snapshots, badges, `src/usage/format.ts`, config overrides, snapshot refresh, the `UsageSnapshot` state shape.

**Compatibility.** `PresenceState` keeps its current usage shape — `usageSnapshots` unchanged, no new field (scans are stateless). The only new state fields are Plan 0003's optional `queueApplied` and `queueOwed` (its 3.5), which older versions drop. dsh records convert into the kit record shape at the totals boundary so one summarizer serves both.

### 3.3 Hook and setup build split

**Chosen approach.** Make the command dispatch in `src/cli/app.ts` load each command implementation through dynamic `import()` and move the shared, hook-needed code (args parsing, state, render, slot sync, hook context) into modules that import neither the installers nor anything Effect-typed. The hook command's static import set becomes the hook graph; a test walks it from the sources (`src/cli.ts` and the hook command) and fails if it reaches an npm package (`effect` included), `setup`, or the installer modules. A batch that brings a kit entry into the hook path — batch 4's `readHookEvent` and, in place of batch 1's process lock, the process-lock and `/node` entries through which Plan 0003's producer checks the worker lock (its 3.3) — adds that entry to an explicit allowlist in the test; `effect` and `zod` never go on it, so a module that parses with a zod/mini schema (2.1) stays out of the hook graph ([Plan 0003](0003-hook-event-queue.md), 3.2). Batch 2's `scanUsage` stays out of it too: Plan 0003's Q1a, which batch 2 follows, takes the built-in scanners off the hook graph. The source graph is the compiled graph: `vp pack` emits one file per source file without tree-shaking (`unbundle: true`, `treeshake: false`), so each built module keeps its source's runtime imports, and walking `src/` needs no build inside `pnpm test`. This lands before the hook-events and setup batches so both migrate onto an already-split build (kit adoption doc, "split build outputs before migrating injection").

- The `bin` target survives: the CLI entry stays `dist/src/cli.js`, so the installed command's shape is unchanged. Recognizing what previous releases installed moves to the kit's marker matching in batch 5, which uses it only to detect those entries so that setup can refuse (3.5): the presence-specific substrings carry over, and the generic `dist/src/cli.js hook` fragment (in `isAgentSignatureCommand`, `src/installers.ts`) deliberately does not — 3.5 records which old command forms that leaves undetected. The markers presence passes to the kit `doctor` also include the installed `HookSpec.command` (3.5), so they match the new command in every command mode.
- Cold start is measured the same way before and after: time `node dist/src/cli.js hook` with a synthetic payload on the built output; the exit condition is "not slower than the pre-split baseline" (it should drop, since setup/installer modules leave the graph). The measurement is manual and its numbers go in the PR description. CI runs no timing test: wall-clock start-up times on shared runners are too noisy for a stable threshold.
- `vp pack` (the separate Vite+ batch) keeps emitting `dist/src/cli.js` as the bin with the legacy hook marker; this batch only restructures imports and depends on that contract, it does not change the bundler.

**Rejected alternative.** Split into two binaries (a hook entry and a management entry): rejected — two bins double the npx surface, break the single installed-command marker, and the dynamic-import dispatch achieves the same graph separation inside one entry.

**Kit entries used.** None yet (this batch enables Effect-free hooks before any Effect import exists).

**Stays in presence.** Everything; this is a restructure with no behavior change (Spec S13).

**Compatibility.** None observable; `node dist/src/cli.js --help` and every command behave as before.

### 3.4 Hook events

**Chosen approach.** The hook command gains `--agent <kitAgentId>` (the `{agent}` placeholder in the installed command, expanded per agent by the kit — [hook-registrations.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/harness/src/domain/bundle/services/hook-registrations.ts)); the payload itself names the event, so the per-event `--event` flag disappears for kit agents. Interpretation moves to `@rivus/agent-kit/harness/events` (Effect-free, no-import-guaranteed):

- `readHookEvent(agent, payload, env)` → `LifecycleEvent` (phase `start/activity/blocked/finish/unknown`, scope, outcome, subagent, tool; sniffs foreign runners like Cursor-run Claude hooks from payload evidence). `LifecycleEvent.nativeEvent` carries the event name as the agent sent it (`read-with-dialect.ts` reads it from the payload's event field — `hook_event_name` for claude-code/codex/gemini-cli, `hookEventName`/`hook_event_name`/`GROK_HOOK_EVENT` for grok, `type` for opencode/pi; empty when the payload names none). Presence's signal rule first normalizes `nativeEvent` **per agent into presence's internal event vocabulary** — the Claude-style names `normalizeEvent`, `applyAgentEvent`, and `isReopenHeartbeat` already key on — and then applies today's rules unchanged: every event that has a rule today keeps today's signal, reopen, and boundary semantics. The kit returns `nativeEvent` exactly as sent and does not canonicalize it (a Grok payload carrying `hookEventName: "user_prompt_submit"` yields `nativeEvent` `user_prompt_submit`), so the per-agent name table maps the native spellings before the lookup — Grok's `session_start`/`user_prompt_submit`/`pre_tool_use`/`post_tool_use`/`stop`/`stop_failure`/`session_end`/`subagent_start`/`subagent_stop` map to `SessionStart`/`UserPromptSubmit`/`PreToolUse`/`PostToolUse`/`Stop`/`StopFailure`/`SessionEnd`/`SubagentStart`/`SubagentStop`, and opencode's `permission.updated` alias resolves to the `permission.asked` row. A name outside the agent's table falls through to the kit phase (`start → start`, `activity → heartbeat`, `finish → finish`, `blocked/unknown → heartbeat` — presence keeps three statuses; a permission dialog is activity). Presence deliberately does not adopt the kit's `reduceLifecycle`/`heartbeatSignal` policy: it ignores session-scope starts ([heartbeat-signal.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/harness/src/domain/lifecycle/policies/heartbeat-signal.ts)) and never starts or finishes subagent events — adopting it would leave sessions unstarted and `<parent>:subagent:<id>` entries (`resolveClaudeHookContext` in `src/hooks/claude.ts`) unfinished. `normalizeEvent` (`src/state.ts`) stays for dsh and as the fallback for payloads without a kit dialect.
- **The event table.** Every event presence registers today, per agent: today's `normalizeEvent` result and boundary flag (`isSessionBoundaryEvent` in `src/state.ts`: start/finish are boundaries, `SubagentStart`/`SubagentStop` are not), the kit phase/scope from the adapter sources, and the signal presence will use. "No today-rule" marks events presence does not register today — for those the kit phase decides. Grok has no source or registration today, so its rows define the new behavior (native spellings, the name mapping above, subagent identity, boundary flags) rather than preserve an existing rule. Boundary status follows the chosen signal exactly as today (start/finish, except subagent events). - **The state machine entry is unchanged.** The mapped signal feeds `applyAgentEvent` (`src/state.ts`) exactly as `normalizeEvent`'s output does today — finish, reopen via native `UserPromptSubmit`, fallback-finish, and the TTL (`expireStaleSessions`) keep their semantics, including creating running sessions on start and finishing subagent sessions. Because the mapping is stateless (name and phase in, signal out), presence persists no new lifecycle state.
- **Session identity stays presence's.** The per-source resolvers (`src/cli/hook-context.ts`, `src/hooks/claude.ts`) keep producing presence session ids and project, including the subagent rule `<parent>:subagent:<agentId>` (`resolveClaudeHookContext` in `src/hooks/claude.ts`) and the existing env fallbacks. For `hook --agent opencode` the session id is `LifecycleEvent.sessionId` from `readHookEvent`; the kit opencode dialect reads `properties.sessionID`, `properties.info.sessionID`, and `properties.part.sessionID`, then `properties.info.id` only on `session.created`, `session.updated`, and `session.deleted` (elsewhere `info.id` can be a message's or a terminal's — [agent-kit#99](https://github.com/PerfectPan/agent-kit/issues/99)), and last the bridge's `currentSessionId` ([opencode.ts](https://github.com/PerfectPan/agent-kit/blob/v0.13.0/packages/harness/src/domain/lifecycle/adapters/opencode.ts)) — the same opencode session id presence stores, so presence adds no payload reading of its own. `currentSessionId` covers events that name no session: `file.edited` carries only the file ([fixture](https://github.com/PerfectPan/agent-kit/blob/v0.13.0/packages/testing/test/fixtures/hooks/opencode.ts), "file.edited names no session"), and opencode can send `session.error` without `sessionID` ([agent-kit#86](https://github.com/PerfectPan/agent-kit/issues/86)). The kit bridge (kit 0.13.0, kit PR [#89](https://github.com/PerfectPan/agent-kit/pull/89)) adds to such an event the session id the dialect read from the latest event that named one, until that session is deleted ([strategies.ts](https://github.com/PerfectPan/agent-kit/blob/v0.13.0/packages/harness/src/domain/bundle/adapters/opencode/strategies.ts)); with several sessions in one plugin instance it is the latest one's, as the old bridge's `lastSessionId` was (`runAgentPresence`, the opencode bridge template built by `buildOpenCodePluginSource` in `src/installers.ts`). So `file.edited` is a heartbeat and a session-less `session.error` a finish, as with the old bridge, and presence keeps no session memory of its own. An event that arrives before the bridge has seen a session carries no id, and the hook skips it with one log line, as it skips every event without a session id (`src/cli/commands/hook.ts`). `pickOpenCodeSessionId` stays only for old-bridge `--source opencode` invocations and goes with the old bridge in batch 5: the old bridge wraps each payload as `{ event }`, which the dialect's root paths never reach, so those invocations keep resolving through `OPENCODE_SESSION_ID` and then `pickOpenCodeSessionId` as before; fixtures cover both bridge generations. The Grok resolver (`src/hooks/grok.ts`) likewise reads its payload with the kit's Grok dialect and composes the subagent id itself (the Grok subagent row of the event table). Payloads are read through kit readers or a zod/mini schema at the boundary, never with new hand-written shape checks (`isRecord`, inline `typeof … === "object"`). The kit's own `sessionId` extraction (documented env `CLAUDE_CODE_SESSION_ID` in [claude-code.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/harness/src/domain/lifecycle/adapters/claude-code.ts)) is not adopted for Claude Code identity, because persisted sessions and render templates key on presence ids and a scheme change would orphan live sessions across the upgrade.

- **Source id mapping.** The hook CLI maps kit agent ids to presence source ids at the boundary (`claude-code → claude`, `gemini-cli → gemini`, others identity, dsh via its own flag). The id it maps is `LifecycleEvent.agent` after `readHookEvent` sniffs the payload, not the `--agent` flag alone: Grok and Cursor also run Claude Code's hooks, so a hook declared for `claude-code` can arrive from either. When it has none — Cursor is the case, since presence has no Cursor source — the hook logs one `hook skipped:` line and ends on today's skip path (the same stdout rule, exit code 0). **Rejected alternatives.** (a) Adopt the kit's lifecycle reducer (`reduceLifecycle` + `heartbeatSignal`) as the signal source: rejected — its policy ignores session-scope starts and never starts or finishes subagent events ([heartbeat-signal.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/harness/src/domain/lifecycle/policies/heartbeat-signal.ts)), which would break running sessions and `<parent>:subagent:<id>` entries; the phase→signal mapping is presence product policy. (b) Keep installing Claude hooks in `settings.json` and print `{}` harder (#89 as originally drafted): rejected — the kit's placement avoids the conflict and its refusal rule turns any future recurrence into a loud install-time error instead of a silent Cursor breakage; the adoption doc names the Cursor permission gate as acceptance work either way.

That shape change is one Codex content-hash re-trust — surfaced as an expected trust prompt by setup (3.5); with the shim the owner chose for the installed hook command (3.5) it is the last one, since later upgrades rewrite the shim instead of the installed command. Old-version and new-version hooks never install side by side: setup refuses while entries of a previous release remain (3.5, S11), except for the old entries it cannot detect (3.5). Presence adds no `blocked` status and no new lifecycle state.

### 3.5 Setup through `/harness`

**Chosen approach.** Presence defines one kit `Bundle` and drives the whole install lifecycle through `@rivus/agent-kit/harness` (Effect-based):

- **Bundle.** `owner: "agent-presence"` (matches the kit's owner pattern; artifacts land under `agent-presence` slugs), `version`: the package version, `digest`: a content hash over the rendered artifacts, `artifacts`: one hooks spec — `command` = the `hook --agent {agent}` invocation plus the required shell fallback, resolved by the owner's decision (Owner decisions, installed hook command) as option (a): setup writes a stable shim file at a fixed path under the presence home and the installed command points at it; the shim runs the pinned version with the explicit registry (as today), so the installed command survives upgrades untouched and setup rewrites only the shim. The options not chosen: (b) keep today's version-pinned `npx --yes --registry=https://registry.npmjs.org @rivus/agent-presence@<version>` (`agentPresenceCommandParts` in `src/installers.ts`) — agents that review hooks by content hash re-ask on every release; (c) unpinned `npx` — rejected: npm would resolve the latest version from the user's default registry on every hook run (a registry request per hook, slower cold start, failure offline), against the hook constraints and batch 3's exit condition. The kit's `HookSpec.command` asks for a command that points at a stable shim and carries no version ([artifact-spec.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/harness/src/domain/bundle/value-objects/artifact-spec.ts)); the absolute form (`AGENT_PRESENCE_HOOK_COMMAND=absolute` → `node <abs>/dist/src/cli.js ...`) keeps working; `events` per kit agent id as in 3.4, `timeoutSeconds: 5`; no `legacyMarkers`. The kit replaces or removes what older versions installed when a bundle names legacy markers (`Bundle.legacyMarkers`, [bundle.ts](https://github.com/PerfectPan/agent-kit/blob/v0.13.0/packages/harness/src/domain/bundle/value-objects/bundle.ts)), and setup leaves that to the previous release's own uninstall (Owner decisions). Presence passes no legacy markers because the owner decided that an upgrade runs the previous release's uninstall first and that setup refuses while that release's entries remain. Issue #92 step 4 ("Supply the `Bundle` (… legacy command markers) so old hooks are replaced") and its acceptance ("old hooks are replaced") asked for those markers and have been updated to match; the kit adoption guide's "Presence" step 5 ("exact legacy command markers") is corrected in [agent-kit#109](https://github.com/PerfectPan/agent-kit/pull/109) (7). Presence instead keeps an inventory of markers for what releases before batch 5 installed — content markers, not just the command substrings from `isAgentSignatureCommand` (`src/installers.ts`) — and uses it only to detect those entries: setup passes it to the kit's read-only legacy listing (previous-release check, below), and `doctor` receives it as `markers` (new commands, below). The kit matches a marker as a plain substring (`text.includes`, blank markers never match) against an artifact file's text, a string entry in a config, or a registration entry's `command` ([legacy-markers.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/harness/src/domain/bundle/policies/legacy-markers.ts)). The inventory:
  - command substrings: `agent-presence hook`, `@rivus/agent-presence`, `agent-signature hook`, `agent-signature.mjs hook` (`isAgentSignatureCommand`). The `dist/src/cli.js hook` fragment from that list is **not** carried into this inventory: it matches any foreign tool invoked at `<checkout>/dist/src/cli.js hook …`, so setup would refuse on a machine whose only match is such a tool, and the remedy it names would make things worse — the previous release's uninstall carries the same fragment and removes that tool's entries (below);
  - opencode plugin file content (identical in both command modes — only `CLI_COMMAND` differs, `buildOpenCodePluginSource` in `src/installers.ts`): `AgentSignaturePlugin` (covers both the `export const` and `export default` forms), `runAgentPresence`;
  - opencode config entries: `./plugins/agent-presence.js` and the legacy `./plugins/agent-signature.js` references (`OPENCODE_PLUGIN_REF` and `LEGACY_OPENCODE_PLUGIN_REF` in `src/installers.ts`) — they detect an old reference whose plugin file is already gone, which no content marker can;
  - Pi extension file content (`buildPiExtensionSource` in `src/installers.ts`): the `@rivus/agent-presence pi extension` header comment (`PI_EXTENSION_MARKER`). The extension file name `agent-presence.ts` (`PI_EXTENSION_FILE_NAME`) is **not** carried into this inventory: a user's own extension that merely mentions that name — for example one checking `existsSync(new URL("./agent-presence.ts", import.meta.url))` — would match it, and setup would refuse on a machine with nothing to uninstall (below). An old Pi settings reference ending in `agent-presence.ts` is therefore not detected and needs manual cleanup: the previous release's uninstall removes only an entry equal to the resolved absolute extension path (`withoutPiAgentPresenceExtension` in `src/installers.ts`), so a relative or `~` reference stays, and presence never wrote such a reference — since Pi support landed (#40), install adds no entry and only removes one equal to that path (`withPiAgentPresenceExtension`). The kit's Pi extension lands on the same path, `~/.pi/agent/extensions/agent-presence.ts` by default (`hookFile` in [pi/strategies.ts](https://github.com/PerfectPan/agent-kit/blob/v0.13.0/packages/harness/src/domain/bundle/adapters/pi/strategies.ts)), so a leftover reference points at the new extension, which Pi already loads from that directory without configuration. The extension file itself is detected by its header.

  Every artifact the old generators produce in either command mode carries a marker — except the documented absolute-command case below — and **a marker must be specific to presence**: it must occur in the artifacts presence's old generators produce and in no file presence does not own. The rule is not stylistic — the kit matches a marker as a plain substring and any one match is enough, so a generic marker makes setup refuse on a machine with nothing to uninstall, sends the user to an uninstall that does not touch the matched file, and makes `doctor` report a foreign hook as a second presence hook. Neither the install Bundle nor `uninstall` carries the inventory, so no marker match makes the kit delete a file. Generic candidates are rejected under this rule: ordinary Pi extensions import `@earendil-works/pi-coding-agent` and subscribe `pi.on("before_agent_start"`, any opencode plugin may define `function mapEvent`, any foreign tool invoked at `<checkout>/dist/src/cli.js hook …` matches the old absolute-path fragment, and a user extension that only checks whether `./agent-presence.ts` exists matches the old file-name marker — none of these may be markers, and batch 5's matrix includes each as a negative fixture next to the positive ones.

  **Old absolute-command entries are the one command form setup cannot detect.** Old command entries in Claude/Codex/Gemini config carry `@rivus/agent-presence` in the npx mode, and the old opencode plugin and Pi extension files carry `AgentSignaturePlugin`/`runAgentPresence` and the Pi header in both modes. But an absolute-form entry (`AGENT_PRESENCE_HOOK_COMMAND=absolute` → `<node> <checkout>/dist/src/cli.js hook …`, `agentPresenceCommandParts` in `src/installers.ts`) from a checkout whose path contains none of the specific substrings matches nothing: `buildAgentPresenceShellCommand` (through `shellQuote`) single-quotes only parts containing characters outside `[A-Za-z0-9_/:=@.-]`, so a typical checkout path is unquoted and no presence-specific quoting fragment exists; candidate command-shape fragments (`hook --source`, `--silent`, the `>/dev/null 2>/dev/null || true` tail) are common shell idioms that would match foreign hook entries and files. Setup therefore does not refuse because of such an entry, and the upgrade procedure is what removes it: the previous release's uninstall matches the common unquoted checkout path with its own `dist/src/cli.js hook` matcher (`isAgentSignatureCommand`). For a checkout path the old builder quotes — one containing a space — the command carries `cli.js' hook`, the old matcher matches none of its markers, and `withoutAgentSignatureHooks` (`src/installers.ts`) leaves the entry, an existing old-version limitation: manual removal, followed by a check of the agent config. An entry left either way — the uninstall skipped, or a quoted checkout path — stays next to the new registrations, and both hooks run per event for that agent until it is removed. `doctor` does not flag it — the kit's `duplicateHooks` ([hook-health.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/harness/src/domain/lifecycle/policies/hook-health.ts)) reports identical commands or several marker-carrying commands, and neither applies here (the commands differ and only the new one carries a marker). The generations covered are those the current `src/installers.ts` generators emit in both command modes, plus the installed older versions whose config references and command substrings the list carries; detection and refusal are exercised from both command modes (npx and `AGENT_PRESENCE_HOOK_COMMAND=absolute`) in batch 5's matrix, with old artifacts generated in both modes and realistic foreign files (a Pi extension importing the SDK and subscribing `before_agent_start`; an opencode plugin defining `mapEvent`; a user extension that only checks whether `./agent-presence.ts` exists; foreign bridges invoking another tool at `/work/team-audit/dist/src/cli.js hook …`) asserted not to match. Presence ships no skills or MCP specs.

- **Flow.** `setup` becomes: legacy-home migration → the previous-release check (next bullet) → login → `planInstall(bundle, { agents: [claude-code, codex, gemini-cli, grok, opencode, pi] })` → display `changes`, `commands`, `expectedTrustPrompts`, `notes`, `droppedHooks` → resolve conflicts strictly within `CONFLICT_CHOICES` (adopt/backup for unmanaged files, force for user-modified/other-owner, nothing for dotfiles-managed or symlinked targets) → `applyInstall(plan)` on the same in-memory plan handle (plans are not serializable; a restart re-plans) → the unchanged dsh opt-in prompt and shutdown-watcher step → provider publishing → `verify("agent-presence", { bundle, agents })` — the bundle builds the desired-artifact set, so verification is three-way and also catches an artifact missing from both disk and ledger ([verify.ts](https://github.com/PerfectPan/agent-kit/blob/v0.11.0/packages/harness/src/application/use-cases/verify.ts)). Setup also takes the queue steps of [Plan 0003](0003-hook-event-queue.md) 3.8: when it finds the queue tombstone, it takes over, deletes the queued records and then the tombstone, and increases the epoch; a setup that the previous-release check stops changes none of them. Write ordering: the leading migration and login steps write before the install plan (credential and home-migration writes are not agent-target writes; the legacy listing writes nothing), and harness planning itself may settle pending ledger operations — Spec S9's write-after-confirmation promise therefore covers the agent-target installation writes from `planInstall` on, which is what the plan display shows.
- **Previous-release check.** Before login, setup asks the kit for the untracked entries, for the same agents, that match the inventory above, through the read-only listing of an owner's legacy entries that [agent-kit#97](https://github.com/PerfectPan/agent-kit/issues/97) requests (3.6); batch 5 waits for the kit release that ships it. The listing changes neither disk nor ledger and reports each entry's agent, location, and artifact kind. When it reports any entry, setup lists each one (its path, and for a hook entry the event and command) and exits non-zero before login and the install confirmation, without writing to any agent target; only the legacy-home migration, which runs before the check, can have prompted. The message asks the user to run the previous release's `agent-presence uninstall` without `--credentials` or `--all`, which keeps credentials, configuration and state, and then `setup` again. It names `npx --yes @rivus/agent-presence@<version> uninstall` with the version a matched hook command pins. When no matched hook command pins one — absolute mode, where only the bridge files and opencode config references are detected, or a machine whose only matches are such files or references — it names `npx --yes @rivus/agent-presence@<last release before batch 5> uninstall`, a version constant batch 5 records (the latest release published when batch 5 merges): that uninstall removes the artifacts at their default paths and matches every command substring and opencode config reference in the inventory, which is drawn from its `src/installers.ts`; a user who set up from a checkout can instead run that checkout's `node <checkout>/dist/src/cli.js uninstall` before updating the checkout. The message never names an unpinned `npx @rivus/agent-presence uninstall`: that resolves to the current release, whose uninstall removes only what the ledger records (new commands, below), so setup would refuse again. The old uninstall removes its artifacts by their default or overridden paths and its hook entries by its own command matcher, so a listed entry it leaves — a copy of the old plugin under another file name, or an entry edited by hand — is removed by hand; the refusal lists each one with its path. Setup does not read previous-release entries from `planInstall` instead: the kit rejects an install plan with `PlanConflict` while any step conflicts, and `PlanConflict` lists only the conflicting steps ([plan-conflict.ts](https://github.com/PerfectPan/agent-kit/blob/v0.13.0/packages/harness/src/domain/install-plan/errors/plan-conflict.ts)), so an unrelated conflict would hide them. Nor does presence build a detection plan of its own: which untracked entries kit planning treats as an owner's legacy artifacts is not part of the kit's published interface, and the kit-first rule (3.6) puts that query in the kit. An old entry at a location the ledger already records — in practice presence's own artifact, which a previous release run after this version's setup overwrote — is not untracked, so the listing does not report it; the install plan shows it as a user-modified artifact whose only choice is `force` (S10). Setup also warns when one of the old install-target override variables (Compatibility below) is set.
- **New commands.** `doctor` → kit `doctor({ owner, agents, markers })` (duplicate-hook, timeout-unit, drift, broken-symlink, lock, ledger checks), with the inventory above as `markers` plus the installed `HookSpec.command` expanded for each agent — the only marker a new absolute-form or shim command carries — so that an old marker-carrying entry next to the new hook is reported as firing twice, whichever command mode the new hook uses (`DoctorOptions.markers`, [doctor.ts](https://github.com/PerfectPan/agent-kit/blob/v0.13.0/packages/harness/src/application/use-cases/doctor.ts)); `inventory` → kit `inventory(options)` (ledger revision, entries, pending operations). `uninstall` → kit `uninstall("agent-presence", { agents })` without `legacyMarkers` — it removes what the ledger records and nothing a previous release installed, which that release's own uninstall removes — plus presence's own removals (dsh plugin, shutdown watcher; `--credentials` behavior unchanged, and `--all` also writes the queue tombstone of [Plan 0003](0003-hook-event-queue.md) 3.8).

- **Installers deleted.** For kit-covered agents the hand-written writers go: Claude/Codex/Gemini hook writers in `src/installers.ts` and `scripts/install-{claude,codex,gemini}-hook.ts` (+ `uninstall-*`), the opencode plugin and Pi extension generators in `src/installers.ts` (the kit adapters generate those bridges themselves), and `scripts/install-{opencode,pi}-*`. **Stay in presence:** the dsh plugin installer and its `cordis.patch.yml` marker block (no kit dsh adapter), the macOS shutdown watcher scripts (not an agent artifact), provider/login/FaaS publishing, legacy-home migration.

**Compatibility.** Upgrade from a release before batch 5: run that release's `agent-presence uninstall` (without `--credentials` or `--all`), then install this release and run `setup`, which refuses while that release's entries remain (previous-release check). ### 3.7 Failures and recovery

- Hooks: unchanged fail-open contract — the CLI swallows errors and exits 0, and its output follows presence's own `{}` rule, not the dialect pass-through: `{}` on every event, including a failure caught inside the CLI on Codex `SessionStart`/`UserPromptSubmit`, whose kit pass-through is `""` (3.4); the shell fallback prints `{}` on process-level failure (S4). A scan failure leaves the previous badge cache intact (`refreshUsageBadgeCache` in `src/cli/usage-badge.ts`).
- Scans: per-source failures arrive as typed `UsageDecodeFailure`/`UsageSourceFailure` items; presence keeps its fail-soft per-source rule and skips that source's contribution for the scan.
- Locks: a state-lock wait that runs past `waitMs` (`AbortSignal.timeout`) surfaces as today's timeout error; a log-lock wait past its ~2.5 s budget maps to `contended` (skip the append), except Plan 0003's dsh usage append, which waits until it holds the lock or a handover interrupts it (3.1); a crashed holder never needs reclamation under SQLite.
- Setup: `planInstall` failures (conflicts outside allowed choices, invalid bundle) abort before any agent-target write; an entry the previous-release check reports ends setup non-zero with the uninstall instruction before login and the install confirmation (3.5); `applyInstall` reports per-artifact results; `verify` after apply catches partial installs; a crashed apply leaves pending operations that `doctor`/`inventory` report and the next plan supersedes.

## 4. Rollout and stability

### 4.1 Gates and rollout stages

Five batches, one per kit area (closing #85/#86; #89 is delivered across the hook-events and setup batches). ### 4.2 Rollback

- Code: revert PRs newest-first; every batch leaves the previous behavior one revert away. Q1 and batches 2-4 change no installed artifacts, so a revert needs no user action; batch 5's revert additionally requires users to re-run the old version's `setup` (next bullet).
- Harness downgrade order (kit adoption doc, "Verification and rollback") — never downgrade by deleting the ledger:
  1. run the new version's `agent-presence uninstall`;
  2. inspect its report for anything `kept`;
  3. run the new version's `verify` and `doctor` until both report no new and no legacy duplicates;
  4. run its `agent-presence worker --stop` ([Plan 0003](0003-hook-event-queue.md) 3.12), which applies the pending queued events and keeps the new version's hooks and worker from recording or starting again;
  5. install the old version and run the old `agent-presence setup`.
     Acceptance exercises exactly this: after new-install → new-uninstall → `worker --stop` → old-setup, the old hooks fire exactly once per event (S12).
- Data: scans are stateless (Owner decisions, usage scan state), so there is no `PresenceState` format change to roll back — `usageSnapshots` keep their shape (3.2), and the old version drops Plan 0003's optional `queueApplied` and `queueOwed` when it loads the file; the kit ledger is additive and ignored by old versions.
