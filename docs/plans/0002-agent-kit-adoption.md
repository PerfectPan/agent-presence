## 1. Background and goals

### 1.1 Current behavior and constraints

This repository is a local CLI whose hook command runs inside other agents' lifecycles. The constraints that shape this plan:

- Hooks must stay fast, bounded, non-interactive, and fail-open (`docs/architecture.md`, "Hook runtime"); Codex hooks always print `{}`.
- Presence comes from lifecycle events, never process scans; each agent is a source in `src/sources.default.json` (`builtin:<id>` entries backed by resolvers in `src/cli/hook-context.ts`).
- Credentials never enter config files, hook commands, logs, or signature URLs (`docs/architecture.md`, trust boundaries).

Current hand-rolled implementations and their locations:

- State lock: `withStateLock` creates a `${statePath}.lock` directory, reclaims it by mtime after `staleMs` (10 s), and throws after `waitMs` (2 s) (`src/state.ts:240-275`, `src/state.ts:326-333`). Callers: `src/cli/slot-sync.ts`, `src/cli/deferred-update.ts`, `src/cli/usage-badge.ts`.
- Log lock: `appendRetainedLogLine` guards concurrent appends with a hardlink owner-token lock (`src/log-retention.ts:65`, marker `agent-presence-log-retention-v1` at `src/log-retention.ts:7`); on `contended` it skips the append, on `unavailable` it appends unlocked (`src/log-retention.ts:15-22`).
- Usage: five per-agent scanners (`src/usage/scan-claude.ts`, `scan-codex.ts`, `scan-gemini.ts`, `scan-opencode.ts`, `scan-pi.ts`) feed `collectWindowUsage`, which computes the calendar window `[startOfLocalDay(now) - (days-1)*24h, now)` and scans sources in parallel, fail-soft (`src/usage/index.ts:54-56`). Presence's `UsageRecord` (`src/usage/types.ts`) has four separate token buckets where `inputTokens` excludes cache.
- Pricing: `resolvePricing` checks config overrides, then a vendored LiteLLM snapshot, then `DEFAULT_PRICING` (`src/usage/pricing.ts:26,43,56`); `resolveRecordCost` prefers a logged cost, else the bucket formula times the pricing multiplier (`src/usage/pricing.ts:122`).
- Hook interpretation: each hook payload is parsed by per-agent resolvers (`src/cli/hook-context.ts`, `src/hooks/claude.ts`), then the event name is mapped through an explicit vocabulary to start/heartbeat/finish, defaulting to heartbeat (`normalizeEvent`, `src/state.ts:290-324`); `applyAgentEvent` (`src/state.ts:149-196`) owns the state machine (finish, reopen via `UserPromptSubmit`, fallback-finish) and a 3-minute TTL expires sessions.
- Installation: `src/installers.ts` writes hooks into each agent's config by hand — Claude command hooks with `timeout: 5000` (`src/installers.ts:59-61`, events at `:23`), Gemini command hooks with Claude's event names and `timeout: 5000` (`src/installers.ts:808,816-824`), an opencode bridge plugin, a Pi bridge extension, and the dsh plugin. `scripts/install-codex-hook.ts` writes Codex hooks with `timeout: 5000` and a `|| echo '{}'` fallback (`scripts/install-codex-hook.ts:8,37-38`). `scripts/install-{claude,codex,gemini}-hook.ts` and the `uninstall-*` variants exist for the isolated-home test flow. The dsh plugin and the macOS shutdown watcher are installed by presence-owned scripts (`src/setup.ts:8-26`).
- Command recognition: `isAgentSignatureCommand` matches installed commands by substrings including `agent-presence hook`, `@rivus/agent-presence`, and `dist/src/cli.js hook` (`src/installers.ts:92-100`).
- CLI structure: `runCli` statically imports every command, so a hook invocation loads the installer and setup code too (`src/cli/app.ts:1-14`). Claude subagent events get their own session entries keyed `<parentSessionId>:subagent:<agentId>` (`src/hooks/claude.ts:37-40`).
- Known drift: Claude and Codex hooks get `timeout: 5000` although both agents read seconds (#85); `GEMINI_EVENTS` uses Claude's event names (#86) (`src/installers.ts:808`); a Cursor agent loads Claude's `settings.json` hooks and maps `PreToolUse` to its own permission hook, where a silent observer blocks (#89).
- Toolchain: the repo pins `minimumReleaseAge: 1440` with `minimumReleaseAgeStrict: true` (`pnpm-workspace.yaml:11-13`), and `engines.node` is `>=22` (`package.json:62-64`). The kit publishes `@rivus/agent-kit` and `@rivus/agent-kit-collab` — 0.8.0 at the time of this revision (published 2026-10-10T16:04Z) — with `engines: >=22.13` and an exact optional peer `effect@4.0.1` (kit `packages/agent-kit/package.json`). Kit source citations in this document were verified against 0.7.0; each batch pins the latest kit release at implementation time and re-verifies its citations against it.

The kit's own migration guide for this repository is [docs/development/adoption.md](https://github.com/PerfectPan/agent-kit/blob/main/docs/development/adoption.md) in the [agent-kit](https://github.com/PerfectPan/agent-kit) repository; its "Public entry inventory", "Presence", "Verification and rollback", and "Known limits" sections are the source of several decisions below. Kit source paths in this document are relative to that repository.

### 1.2 Problem

Presence duplicates, and has already drifted from, what the kit now ships: per-agent hook vocabularies (#86), timeout units (#85), permission-gate semantics (#89), usage transcript decoding, pricing, install/uninstall flows, and process locks. Every new agent or decoding fix currently means hand-maintaining all of it here. The kit ships these as versioned, tested entries; adopting them removes the duplication and fixes #85/#86/#89 in the same motion.

### 1.3 Goals and success criteria

- Spec 0002 scenarios S1-S13 pass, each mapped to a batch and test in section 6.
- The five hand-rolled usage scanners, the hand-rolled pricing resolution, the hand-rolled hook/config installers for kit-covered agents, and both hand-rolled locks are deleted and replaced by kit entries (the deleted-modules list in issue #92).
- The hook entry's import graph contains no `effect` and no setup code, and the hook cold start does not get slower.
- `dist/src/cli.js hook` keeps working as the installed hook command (its generic fragment is no longer a legacy marker — 3.5 records the consequences).
- Install, verify, doctor, uninstall, and the documented downgrade pass under an isolated `HOME` for every kit-covered agent.
- No credentials or private paths enter config files, hook commands, ledger contents, logs, or this repository.

### 1.4 Non-goals

- A Cursor source (the kit ships no Cursor usage decoder; see 3.6).
- A blocked presence status driven by the kit's blocked lifecycle phase (presence keeps three statuses).
- New agents beyond Grok.
- Toolchain changes (lint-config v0.6.0, the Vite+ build) — delivered separately per issue #92's ordering; this plan only consumes them.

## 2. Outline

### 2.1 Design principles

- One kit area per PR, in dependency order, each with old-behavior and new-behavior evidence (kit adoption doc, "Verification and rollback").
- The kit owns agent semantics: which events exist, what they mean, where hooks install, how transcripts decode. Presence owns its product policy: source ids, the state machine, TTL, rendering, providers.
- A kit gap is fixed in the kit and released first, never worked around in presence (kit adoption doc, "Known limits").
- The hook path never imports Effect or setup code; the single `Effect.runPromiseExit` lives at the CLI root for setup-shaped commands.

### 2.2 Boundaries and responsibilities

| Area         | Kit owns                                                                                  | Presence owns                                                                  |
| ------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Process lock | `acquireProcessLock` mechanics (SQLite exclusive lock, file fallback, holder diagnostics) | Which paths are locked and the wait/skip policy per call site                  |
| Usage        | Transcript decoding per agent, dedup                                                      | Windows, per-source snapshots, badges, dsh usage events                        |
| Pricing      | Price tables, LiteLLM conversion, cost formula                                            | Snapshot refresh, config overrides, fallback table, badge rendering            |
| Hook events  | Payload → lifecycle interpretation, dialect rules (timeouts, output, gates)               | Source ids, session identity, presence state machine, TTL/reopen               |
| Install      | Placement strategies, ledger, plan/apply/verify/doctor/inventory/uninstall                | Bundle definition, setup UX, dsh plugin, shutdown watcher, provider publishing |

### 2.3 Main path

After all batches: a hook invocation resolves the presence source from `--agent {agent}`, interprets the payload with `readHookEvent` (`@rivus/agent-kit/harness/events`), feeds the phase through the presence-owned signal mapping into the unchanged presence state machine under the state lock now provided by `acquireProcessLock`, and rescans the usage window with `scanUsage` (`@rivus/agent-kit/transcript/usage`), replacing that window's per-source snapshots priced through `@rivus/agent-kit/cost`. `setup` builds a kit `Bundle`, shows the plan from `planInstall`, applies it, and verifies; `doctor`, `inventory`, and `uninstall` are kit-backed CLI commands. The hook command import graph contains neither `effect` nor setup code.

## 3. Detailed design

### 3.1 Process lock

**Chosen approach.** Replace `withStateLock`'s mkdir implementation with the kit's `acquireProcessLock(platform, path, options)` from `@rivus/agent-kit-collab/process-lock` ([source](https://github.com/PerfectPan/agent-kit/blob/main/packages/agent-kit-collab/src/process-lock/application/use-cases/acquire-process-lock.ts)): with `platform.sqlite` present, `path` is a SQLite database held in `locking_mode=EXCLUSIVE`, so the kernel releases the lock when the process exits or crashes; a `.holder` file next to it records the holder for diagnostics. Without SQLite the kit falls back to an identity-bearing lock file with dead-holder reclamation. The platform comes from `createNodePlatform()` (`@rivus/agent-kit/node`).

- The lock target moves to a new path, `${statePath}.lock.db` — never the state JSON itself (the SQLite mechanism turns `path` into a database), and never the old `${statePath}.lock`: the previous version deletes that path on release and on stale reclaim (`rm(lockPath, ...)` at `src/state.ts:259-262,271-273`), so a database living there would be deleted under a live holder during an upgrade overlap, and a third process could then lock a fresh file at that path. The old lock directory is left alone (no pre-clean); with distinct paths, neither version deletes the other's lock.
- `withStateLock(statePath, fn, { waitMs })` keeps its signature so its callers (`src/cli/slot-sync.ts`, `src/cli/deferred-update.ts`, `src/cli/usage-badge.ts`) do not change; internally it calls `acquireProcessLock` with `wait: true` and `signal: AbortSignal.timeout(waitMs)` — the kit's `wait` flag has no built-in budget, so the deadline is the signal — and maps an abort to the same timeout error it throws today. The parent directory is created before acquiring (the kit requires an existing directory). The mkdir/stale-mtime code (`src/state.ts:240-275,326-333`) is deleted.
- Log retention: `acquireLogLock` (`src/log-retention.ts:65-176`) is replaced by `acquireProcessLock` with `wait: true` and `signal: AbortSignal.timeout(LOG_LOCK_WAIT_ATTEMPTS * LOG_LOCK_RETRY_MS)` — today's bounded wait, 250 attempts × 10 ms ≈ 2.5 s (`src/log-retention.ts:11,76-104`). A timeout or `ProcessLockHeld` maps to today's `contended` (skip the append) and an unexpected acquire failure keeps today's `unavailable` (append unlocked) fail-open behavior. The hardlink code and the `agent-presence-log-retention-v1` marker are deleted. Batch 1 uses only plain kit entries, so it adds no `effect` dependency (the exact pin lands with `/harness` in 3.5).

**Rejected alternative.** Keep the mkdir lock and only fix its edge cases (stale-mtime races, cross-platform `link()` gaps): rejected because crash-safety is exactly what the kit's kernel-released SQLite lock provides and presence cannot match it without reimplementing it — this is the kit area the adoption starts with per issue #92.

**Kit entries used.** `@rivus/agent-kit-collab/process-lock` (`acquireProcessLock`, `ProcessLock`, `ProcessLockHeld`), `@rivus/agent-kit/node` (`createNodePlatform`).

**Stays in presence.** Which paths are locked, wait/skip policy, all state and log logic.

**Compatibility.** `engines.node` rises to `>=22.13` (kit Node adapters; `package.json:62-64` changes). Mixed-version overlap: a previous-version hook (mkdir lock at `${statePath}.lock`) and this version's hook (SQLite lock at `${statePath}.lock.db`) still do not exclude each other — different paths and primitives — accepted because hooks are short-lived and state writes stay atomic (7); neither deletes the other's lock, though. A holder that is alive but stuck now makes waiters time out after `waitMs` (2 s) instead of being reclaimed after 10 seconds of mtime staleness; the crashed-holder case improves from timed reclaim to immediate kernel release.

### 3.2 Usage and pricing

**Chosen approach.** Replace the five scanners with one stateless `scanUsage(platform, { agents, since, until })` call per window ([source](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/application/use-cases/scan-usage.ts)) — no persisted `UsageScanState`. Every scan re-reads the whole window from `since: <window start>`, prices the emitted records with the current pricing, and replaces that window's per-source snapshots exactly as `collectWindowUsage` and the badge cache do today (`src/usage/index.ts`, `src/cli/usage-badge.ts`). This is the cost model presence already has — it rescans every window today. It keeps windows independent, makes overlapping scans idempotent (two scans of one window produce the same snapshot), and applies price changes on the next scan. `scanUsage` returns an async iterable of `UsageRecord | UsageDecodeFailure | UsageSourceFailure`; the record carries `usage` (kit convention: `inputTokens` includes cache reads and writes, `outputTokens` includes reasoning — [usage.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/domain/usage/value-objects/usage.ts)), optional `costUsd`, and optional `pricingMultiplier`.

- **Source selection stays table-driven.** `collectWindowUsage` keeps its window math (`src/usage/index.ts:54-56`) and resolves sources through `billableSources` (`src/sources.ts:292-331`): `enabled: false`, config-overridden entries, custom handler sources, and table order keep today's semantics. Built-in sources with kit decoders map to kit agent ids and are batched into one `scanUsage` call per window; a custom handler source keeps its handler scanner, and dsh keeps its own scanner, merged at the totals boundary. A same-day hook refresh scans only the boundary's owning source (`src/cli/usage-badge.ts:72-92`), as today. The `includeHandlers: false` trust boundary is untouched.
- **Totals mapping (badge parity).** Presence's old four-bucket total equals `usage.inputTokens + usage.outputTokens` (kit input includes cache). Badges keep rendering `totalTokens` + `$cost`, so S7's token totals are identical by construction. Cost: `priceUsage` ([price-usage.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/cost/src/domain/pricing/services/price-usage.ts)) uses the same term order as presence's `resolveRecordCost` (`src/usage/pricing.ts:122`) — logged cost wins unmultiplied, token cost times the record's multiplier — so dollars agree.
- **Pricing table.** `createPricing(table, { overrides, fallback })` from `@rivus/agent-kit/cost` replaces `resolvePricing`'s merged-table lookup (`src/usage/pricing.ts:56`). The snapshot is injected directly: its `prices` entries are already per-million `input`/`output`/`cacheWrite`/`cacheWrite1h`/`cacheRead` (`src/usage/litellm-pricing.json`), which is `createPricing`'s form. `fromLiteLLM` ([from-litellm.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/cost/src/domain/pricing/adapters/from-litellm.ts)) is not applied to the snapshot — it expects raw LiteLLM entries with `input_cost_per_token`/`output_cost_per_token` and would produce an empty table for this snapshot, silently degrading prices (claude-opus-4-8 would fall back from its snapshot input price to the broad opus price). If used at all, `fromLiteLLM` belongs where raw LiteLLM data enters — the snapshot refresh. Presence keeps: snapshot storage/refresh, `usage.pricing` config overrides (passed as `overrides`), and `DEFAULT_PRICING` (`src/usage/pricing.ts:26`) as `fallback`. Unknown models still render tokens with n/a cost (`UsageTotals.costUsd` absent).
- **Trailing-request lag (behavior change, per decoder; applies to stateless scans too).** Finalization is per decoder, not one uniform rule, and none of it depends on scan state: the Claude Code decoder withholds a request while it is among the four most recent in its conversation lane (`OPEN_PER_LANE = 4`, released at `lane.open.length > OPEN_PER_LANE`, [claude-code.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/domain/usage/adapters/claude-code.ts)) — a withheld request is released once four newer requests have been written in its lane, never by a single later request (a lane holding one open request stays withheld when a second is written) — or until the source is decoded with `final`, which `scanUsage` does once the source has been quiet for 30 minutes ([scan-usage.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/application/use-cases/scan-usage.ts)); the opencode decoder returns `"running"` for a message in the SQLite database without `time.completed` (which opencode sets when the message ends, also on error or abort) and counts it only once completed or the source is finalized ([usage.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/domain/usage/adapters/opencode/usage.ts)), while a message in the legacy `storage/message` JSON store always carries a settle time and counts immediately ([usage-decoders/opencode.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/application/services/usage-decoders/opencode.ts)); the Gemini CLI, Pi, and Codex decoders emit a request's usage as soon as its record is complete, without waiting for quiet ([gemini-cli.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/domain/usage/adapters/gemini-cli.ts), [pi.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/domain/usage/adapters/pi.ts), [codex.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/domain/usage/adapters/codex.ts)). After adoption, snapshots and badges leave out a still-active Claude Code source's newest requests (up to four per lane) and an opencode source's still-running database messages, while Gemini/Pi/Codex trailing requests count as today. Presence today counts every record it reads immediately (`src/usage/scan-claude.ts:49`). Whether to accept the lag is an open decision (Owner decisions, 7).
- **Grok.** Batch 2 wires Grok's kit-backed usage decoding (kit agent id `grok` batched into the `scanUsage` call), and batch 4 adds the `builtin:grok` source entry (`src/sources.default.json`) together with its hook resolver (3.4) — the source entry has to exist before Grok lifecycle or usage is observable, and `resolveHookContextForSource` resolves nothing for an absent entry (`src/sources.ts:359-361`), so no Grok presence or usage change is observable until batch 4 (no hooks install until 3.5). Presence source id `grok` equals the kit agent id.
- **Corrections adopted** (each cited, each fixture-tested, per the adoption doc's "do not hide decoding corrections in a broad tolerance"):
  - Codex per-record tier: the kit reads each record's own `serviceTier` and applies `codexPricingMultiplier` per record ([codex.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/domain/usage/adapters/codex.ts)); presence applied the current `~/.codex/config.toml` tier to every record in the window (`src/usage/scan-codex.ts:57-58,277-284`).

  - Gemini tool tokens counted: a record's input tokens become `input + (tool ?? 0)` ([gemini-cli.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/domain/usage/adapters/gemini-cli.ts)), where `src/usage/scan-gemini.ts` omits tool tokens.

  - Absent-versus-zero: counts a transcript does not report stay absent instead of 0.
  - opencode store and fallback: the kit reads the SQLite message store and uses the legacy `storage/message` session directories only when no database exists ([opencode.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/sessions/src/application/services/usage-decoders/opencode.ts)) — the legacy fallback itself is not a kit gap. The real difference: when `opencode.db` exists but cannot be read, the kit reports a source failure while presence falls back to legacy JSON (`docs/architecture.md` usage section). Current opencode (1.18.11) keeps sessions in `opencode.db` (`storage/` holds only `migration` and `session_diff`), so the fallback difference is the fixture-tested edge — see 3.6.

**Rejected alternatives.** (a) Keep presence's scanners and only port individual fixes: rejected — every future agent/decoding fix would stay hand-rolled, which is the problem. (b) Let the kit own windows and badges too: rejected — presence's per-source snapshot and aggregate rules (`src/cli/usage-badge.ts:88-179`) are product policy the kit does not ship, and moving them would break the downgrade story for no kit benefit. (c) Persist the kit's `UsageScanState` cursors and store incremental deltas (per-day buckets): rejected — the persisted cursors partition the window, so a scan reads only what was written since its cursor and a second scan of a quiet window yields nothing; overlapping scans then double count or drop the first scan's usage — atomic cursor and aggregate commits alone do not cure that, because two readers of the same cursor still need serialization or revision checks; price changes apply only to not-yet-counted records, leaving stale prices in stored buckets; and each window rollover must decide between subtracting an expired contribution from a live aggregate or re-deriving it. The stateless rescan has none of these modes and matches the cost model presence already has.

**Kit entries used.** `@rivus/agent-kit/transcript/usage` (`scanUsage`, `decodeUsage`, `UsageRecord`, failure item types), `@rivus/agent-kit/cost` (`createPricing`, `fromLiteLLM`, `priceUsage` via `costOf`, `summarize`, `calendarWindow` if needed for self-checks), `@rivus/agent-kit/node` (platform).

**Stays in presence.** dsh usage events (host-owned protocol), windows, snapshots, badges, `src/usage/format.ts`, config overrides, snapshot refresh, the `UsageSnapshot` state shape.

**Compatibility.** `PresenceState` keeps its current usage shape — `usageSnapshots` unchanged, no new field (scans are stateless). dsh records convert into the kit record shape at the totals boundary so one summarizer serves both.

### 3.3 Hook and setup build split

**Chosen approach.** Make the command dispatch in `src/cli/app.ts` load each command implementation through dynamic `import()` and move the shared, hook-needed code (args parsing, state, render, slot sync, hook context) into modules that import neither the installers nor anything Effect-typed. The hook command's static import set becomes the hook graph; a test walks the compiled graph (entry `dist/src/cli.js` with `hook`) and fails if it reaches `effect`, `setup`, or the installer modules. This lands before the hook-events and setup batches so both migrate onto an already-split build (kit adoption doc, "split build outputs before migrating injection").

- The `bin` target survives: the CLI entry stays `dist/src/cli.js`, so the installed command's shape is unchanged. Command recognition moves to the kit's marker matching in batch 5 (3.5): the presence-specific substrings carry over, and the generic `dist/src/cli.js hook` fragment (`src/installers.ts:98`) deliberately does not — 3.5 records which old command forms that leaves unrecognized. The kit's `HookSpec.command` (3.5) stays recognizable by presence's command markers — the `legacyMarkers` list is presence-defined and extends to the shim path if the shim option wins.
- Cold start is measured the same way before and after: time `node dist/src/cli.js hook` with a synthetic payload on the built output; the exit condition is "not slower than the pre-split baseline" (it should drop, since setup/installer modules leave the graph).
- `vp pack` (the separate Vite+ batch) keeps emitting `dist/src/cli.js` as the bin with the legacy hook marker; this batch only restructures imports and depends on that contract, it does not change the bundler.

**Rejected alternative.** Split into two binaries (a hook entry and a management entry): rejected — two bins double the npx surface, break the single installed-command marker, and the dynamic-import dispatch achieves the same graph separation inside one entry.

**Kit entries used.** None yet (this batch enables Effect-free hooks before any Effect import exists).

**Stays in presence.** Everything; this is a restructure with no behavior change (Spec S13).

**Compatibility.** None observable; `node dist/src/cli.js --help` and every command behave as before.

**Chosen approach.** The hook command gains `--agent <kitAgentId>` (the `{agent}` placeholder in the installed command, expanded per agent by the kit — [hook-registrations.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/bundle/services/hook-registrations.ts)); the payload itself names the event, so the per-event `--event` flag disappears for kit agents. - **Timeouts (#85).** The installed `HookSpec` carries `timeoutSeconds: 5`; `hookRegistrations` converts it per dialect unit — seconds for claude-code, codex, grok, cursor; `× 1000` for gemini-cli's milliseconds ([hook-registrations.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/bundle/services/hook-registrations.ts)). Installed results: Claude `5`, Codex `5`, Grok `5`, Gemini `5000`. Claude's shared per-event budget becomes 5 s (under its 60 s ceiling). Today's `timeout: 5000` for Claude/Codex (`src/installers.ts:60`, `scripts/install-codex-hook.ts:38`) is the #85 bug.
- **Gemini events (#86).** `HookSpec.events["gemini-cli"] = [SessionStart, BeforeAgent, BeforeTool, AfterTool, AfterAgent, SessionEnd]` — the kit gemini dialect's real names ([gemini-cli.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/lifecycle/adapters/gemini-cli.ts)), which accepts `SessionStart` and `SessionEnd`. `SessionStart`/`SessionEnd` are registered and firing today and keep their signals (keeping `SessionStart` preserves today's session-start signal); `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, and `Stop` are Claude-only names the gemini dialect rejects as invalid — that is exactly #86 — and they leave the install set, replaced by Gemini's own per-turn names. The gemini adapter's legacy sources remove the previous entries under those four names from `settings.json#/hooks`.
- **Permission semantics (#89).** Claude hooks install via the kit's native-plugin strategy into `~/.claude/skills/<owner>/hooks/hooks.json`, which Cursor and Grok do not read — so Cursor stops seeing presence's `PreToolUse` at all. Should a strategy ever place a presence hook where a foreign runner would execute it on a gate, `hookRegistrations` refuses the observer registration (`HookSpecRejected { reason: "blocking-gate" }`, including the renamed-runBy case); that rejection propagates as a `planInstall` planning error ([hook-placement.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/bundle/services/hook-placement.ts), [plan-install.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/bundle/services/plan-install.ts)) so setup fails loudly before any agent-target write — it is not reported as a dropped hook (`DroppedHook` covers only presence's own registration being dropped because another agent's placed file already fires it, `hook-placement.ts:47-59`). As a second belt: on gate events the installed command's `|| echo '{}'` fallback (already present for Codex, `scripts/install-codex-hook.ts:37`) applies to every command hook, and the hook CLI's `writeHookOutput` (`src/cli/hook-context.ts:89`) prints `{}`. That output rule is presence-owned and kept deliberately: the kit's Codex dialect marks the context events (`SessionStart`, `UserPromptSubmit`) as `passThrough: ""` ([codex.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/lifecycle/adapters/codex.ts)), so consulting the dialect pass-through alone would silence successful Codex context events and break the unchanged-behavior rule that Codex hooks always print `{}`; tests cover successful Codex context events as well as failures. Cursor's own empty-stdout behavior on gates is undocumented in the kit dialect (`emptyStdout: "undocumented"`, [cursor.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/lifecycle/adapters/cursor.ts)); acceptance covers it as an owner-authorized real-agent check (Owner decisions).
- **Registered event sets.** Claude Code keeps today's set (`src/installers.ts:23-33`); Codex keeps `[SessionStart, UserPromptSubmit, PreToolUse, Stop]`; Gemini's set becomes `[SessionStart, BeforeAgent, BeforeTool, AfterTool, AfterAgent, SessionEnd]` (the #86 bullet above); Grok registers the same nine-event shape in its own hook file (`~/.grok/hooks/<owner>.json`, the dialect's PascalCase keys — the same names as Claude Code's set; the snake_case spellings in the event table are what Grok sends and what `readHookEvent` reports, accepted only as reading-side aliases: `events.grok` with snake_case names is rejected as `unknown-event`), and batch 4 also adds the `builtin:grok` source entry to `src/sources.default.json` with its hook resolver — moved from batch 2, because `resolveHookContextForSource` resolves nothing for an absent entry (`src/sources.ts:359-361`) and the lifecycle tests need a real source; opencode and Pi install kit-generated bridge plugins/extensions that forward native payloads, replacing presence's hand-written bridge sources; dsh is untouched. Every name in the new registered sets exists in its kit dialect (verified against the adapter sources), so nothing is refused as `unknown-event`; the four Gemini names the dialect rejects are exactly #86 and leave the install set. The event table above is the contract batch 4 implements and tests against.
- **Source id mapping.** The hook CLI maps kit agent ids to presence source ids at the boundary (`claude-code → claude`, `gemini-cli → gemini`, others identity, dsh via its own flag). The id it maps is `LifecycleEvent.agent` after `readHookEvent` sniffs the payload, not the `--agent` flag alone: Grok and Cursor also run Claude Code's hooks, so a hook declared for `claude-code` can arrive from either. Presence records the event on the presence source of that sniffed agent when it has one (`claude-code → claude`, `gemini-cli → gemini`, and `codex`, `grok`, `opencode`, `pi` by the same id). When it has none — Cursor is the case, since presence has no Cursor source — the hook logs one `hook skipped:` line and ends on today's skip path (the same stdout rule, exit code 0). Counting that payload as Claude would attribute another product's session to Claude; skipping it keeps the fail-open hook contract and leaves state unchanged. Persisted state, templates, and configs never see kit ids.

**Rejected alternatives.** (a) Adopt the kit's lifecycle reducer (`reduceLifecycle` + `heartbeatSignal`) as the signal source: rejected — its policy ignores session-scope starts and never starts or finishes subagent events ([heartbeat-signal.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/lifecycle/policies/heartbeat-signal.ts)), which would break running sessions and `<parent>:subagent:<id>` entries; the phase→signal mapping is presence product policy. (b) Keep installing Claude hooks in `settings.json` and print `{}` harder (#89 as originally drafted): rejected — the kit's placement avoids the conflict and its refusal rule turns any future recurrence into a loud install-time error instead of a silent Cursor breakage; the adoption doc names the Cursor permission gate as acceptance work either way.

**Kit entries used.** `@rivus/agent-kit/harness/events` (`readHookEvent`, `builtinHookDialects`, `HookOutput`), `@rivus/agent-kit/catalog` (`builtinCodingAgents`, id types).

**Stays in presence.** Session identity and env fallbacks, the state machine, TTL/reopen/fallback-finish, `writeHookOutput`'s policy, dsh hook flow, boundary-badge refresh rules (`isSessionBoundaryEvent`, `src/state.ts:282-288`).

**Compatibility.** New installs carry `--agent {agent}` instead of per-event `--source/--event`; the `hook` command keeps accepting `--source/--event` with today's meaning, because hooks installed by previous versions execute the upgraded code after a package update and before `setup` runs again. That shape change is one Codex content-hash re-trust — surfaced as an expected trust prompt by setup (3.5); under the hook-command decision's shim option (3.5, 7) it is the last one, since later upgrades rewrite the shim instead of the installed command. Old-version and new-version hooks never install side by side (legacy markers replace them, S11). Presence adds no `blocked` status and no new lifecycle state.

### 3.5 Setup through `/harness`

**Chosen approach.** Presence defines one kit `Bundle` and drives the whole install lifecycle through `@rivus/agent-kit/harness` (Effect-based):

- **Bundle.** `owner: "agent-presence"` (matches the kit's owner pattern; artifacts land under `agent-presence` slugs), `version`: the package version, `digest`: a content hash over the rendered artifacts, `artifacts`: one hooks spec — `command` = the `hook --agent {agent}` invocation plus the required shell fallback, whose resolution is an open decision (7): (a) recommended — setup writes a stable shim file at a fixed path under the presence home and the installed command points at it; the shim runs the pinned version with the explicit registry (as today), so the installed command survives upgrades untouched and setup rewrites only the shim; (b) keep today's version-pinned `npx --yes --registry=https://registry.npmjs.org @rivus/agent-presence@<version>` (`src/installers.ts:759-768`) — agents that review hooks by content hash re-ask on every release; (c) unpinned `npx` — rejected: npm would resolve the latest version from the user's default registry on every hook run (a registry request per hook, slower cold start, failure offline), against the hook constraints and batch 3's exit condition. The kit's `HookSpec.command` asks for a command that points at a stable shim and carries no version ([artifact-spec.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/bundle/value-objects/artifact-spec.ts)); the absolute form (`AGENT_PRESENCE_HOOK_COMMAND=absolute` → `node <abs>/dist/src/cli.js ...`) keeps working whichever option is chosen. With (a), the presence-defined `legacyMarkers` also cover the shim path so an old shim is recognized; `events` per kit agent id as in 3.4, `timeoutSeconds: 5`; `legacyMarkers`: a content-marker inventory, not just the command substrings from `isAgentSignatureCommand` (`src/installers.ts:92-100`). The kit matches a marker as a plain substring (`text.includes`, blank markers never match) against an artifact file's text, a string entry in a config, or a registration entry's `command` ([legacy-markers.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/bundle/policies/legacy-markers.ts)). The inventory:
  - command substrings: `agent-presence hook`, `@rivus/agent-presence`, `agent-signature hook`, `agent-signature.mjs hook` (`src/installers.ts:92-100`). The `dist/src/cli.js hook` fragment from that list is **not** carried into this inventory: it matches any foreign tool invoked at `<checkout>/dist/src/cli.js hook …`, and the kit plans an untracked legacy match as a delete with no pre-image (below), so it would make setup or uninstall delete user files;
  - opencode plugin file content (identical in both command modes — only `CLI_COMMAND` differs, `src/installers.ts:378-499`): `AgentSignaturePlugin` (covers both the `export const` and `export default` forms), `runAgentPresence`;
  - opencode config entries: `./plugins/agent-presence.js` and the legacy `./plugins/agent-signature.js` references (`src/installers.ts:35-36`) — the bare command substrings alone would miss an old explicit reference after the new uninstall deletes the plugin file, and an absolute-command bridge from a checkout whose path carries no marker;
  - Pi extension file content (`src/installers.ts:503-598`): the `@rivus/agent-presence pi extension` header comment (`PI_EXTENSION_MARKER`, `src/installers.ts:39`). The extension file name `agent-presence.ts` (`src/installers.ts:38`) is **not** carried into this inventory: a user's own extension that merely mentions that name — for example one checking `existsSync(new URL("./agent-presence.ts", import.meta.url))` — would match it, and the kit plans an untracked match as a delete with no pre-image (below), so setup or uninstall would delete the user's file. Until agent-kit#81 scopes file-name markers to configuration references (3.6), an old Pi settings reference ending in `agent-presence.ts` is unmatched and needs manual cleanup; the extension file itself is still matched by its header.

  Every artifact the old generators produce in either command mode carries a marker — except the documented absolute-command case below — and **a marker must be specific to presence**: it must occur in the artifacts presence's old generators produce and in no file presence does not own. The rule is not stylistic — the kit matches a marker as a plain substring and any one match is enough, and an untracked match is planned as a removal with `removal: "delete"` and no pre-image captured ([conflict-detection.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/install-plan/policies/conflict-detection.ts), the `legacy` removal step), so a generic marker makes setup or uninstall delete a user's own file. Generic candidates are rejected under this rule: ordinary Pi extensions import `@earendil-works/pi-coding-agent` and subscribe `pi.on("before_agent_start"`, any opencode plugin may define `function mapEvent`, any foreign tool invoked at `<checkout>/dist/src/cli.js hook …` matches the old absolute-path fragment, and a user extension that only checks whether `./agent-presence.ts` exists matches the old file-name marker — none of these may be markers, and batch 5's matrix includes each as a negative fixture next to the positive ones.

  **Old absolute-command entries are the one gap this leaves.** Old command entries in Claude/Codex/Gemini config carry `@rivus/agent-presence` in the npx mode, and the old opencode plugin and Pi extension files carry `AgentSignaturePlugin`/`runAgentPresence` and the Pi header in both modes. But an absolute-form entry (`AGENT_PRESENCE_HOOK_COMMAND=absolute` → `<node> <checkout>/dist/src/cli.js hook …`, `src/installers.ts:371-376`) from a checkout whose path contains none of the specific substrings matches nothing: `buildAgentPresenceShellCommand` (`src/installers.ts:781-783`) single-quotes only parts containing characters outside `[A-Za-z0-9_/:=@.-]`, so a typical checkout path is unquoted and no presence-specific quoting fragment exists; candidate command-shape fragments (`hook --source`, `--silent`, the `>/dev/null 2>/dev/null || true` tail) are common shell idioms that would match foreign hook entries and files. These entries are therefore **not recognized automatically**: after an upgrade they stay next to the new registrations and both hooks run per event for those agents until the old entry is removed. `doctor` does not flag them — the kit's `duplicateHooks` ([hook-health.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/domain/bundle/services/hook-health.ts)) reports identical commands or several marker-carrying commands, and neither applies here (the commands differ and only the new one carries a marker). Manual cleanup: for the common unquoted checkout path the previous version's uninstall removes the old entries (its own `dist/src/cli.js hook` matcher, `src/installers.ts:92-100`, matches them); for a checkout path the old builder quotes — one containing a space — the command carries `cli.js' hook` and the old matcher matches none of its markers, so `withoutAgentSignatureHooks` (`src/installers.ts:58`) leaves those entries too, an existing old-version limitation: manual removal, followed by a check of the agent config, is the cleanup for such installs. The enabling kit gap — marker scope per legacy-source kind, plus a pre-image for untracked legacy removals so a wrong match is recoverable — is filed as [agent-kit#81](https://github.com/PerfectPan/agent-kit/issues/81) (3.6), and batch 5 is blocked on its release. Setup showing every planned legacy removal before applying (3.5 flow) is a mitigation, not a fix. The generations covered are those the current `src/installers.ts` generators emit in both command modes, plus the installed older versions whose config references and command substrings the list carries; upgrade and uninstall are exercised from both command modes (npx and `AGENT_PRESENCE_HOOK_COMMAND=absolute`) in batch 5's matrix, with old artifacts generated in both modes and realistic foreign files (a Pi extension importing the SDK and subscribing `before_agent_start`; an opencode plugin defining `mapEvent`; a user extension that only checks whether `./agent-presence.ts` exists; foreign bridges invoking another tool at `/work/team-audit/dist/src/cli.js hook …`) asserted not to match. Presence ships no skills or MCP specs.

- **Flow.** `setup` becomes: legacy-home migration → login → `planInstall(bundle, { agents: [claude-code, codex, gemini-cli, grok, opencode, pi] })` → display `changes`, `commands`, `expectedTrustPrompts`, `notes`, `droppedHooks` → resolve conflicts strictly within `CONFLICT_CHOICES` (adopt/backup for unmanaged files, force for user-modified/other-owner, nothing for dotfiles-managed or symlinked targets) → `applyInstall(plan)` on the same in-memory plan handle (plans are not serializable; a restart re-plans) → the unchanged dsh opt-in prompt and shutdown-watcher step → provider publishing → `verify("agent-presence", { bundle, agents })` — the bundle builds the desired-artifact set, so verification is three-way and also catches an artifact missing from both disk and ledger ([verify.ts](https://github.com/PerfectPan/agent-kit/blob/main/packages/harness/src/application/use-cases/verify.ts)). ### 3.7 Failures and recovery

- Hooks: unchanged fail-open contract — the CLI swallows errors and exits 0, and its output follows presence's own `{}` rule, not the dialect pass-through: `{}` on every event, including a failure caught inside the CLI on Codex `SessionStart`/`UserPromptSubmit`, whose kit pass-through is `""` (3.4); the shell fallback prints `{}` on process-level failure (S4). A scan failure leaves the previous badge cache intact (`src/cli/usage-badge.ts:124-126`).
- Scans: per-source failures arrive as typed `UsageDecodeFailure`/`UsageSourceFailure` items; presence keeps its fail-soft per-source rule and skips that source's contribution for the scan.
- Locks: a state-lock wait that runs past `waitMs` (`AbortSignal.timeout`) surfaces as today's timeout error; a log-lock wait past its ~2.5 s budget maps to `contended` (skip the append); a crashed holder never needs reclamation under SQLite.
- Setup: `planInstall` failures (conflicts outside allowed choices, invalid bundle) abort before any agent-target write; `applyInstall` reports per-artifact results; `verify` after apply catches partial installs; a crashed apply leaves pending operations that `doctor`/`inventory` report and the next plan supersedes.

## 4. Rollout and stability

### 4.1 Gates and rollout stages

Five batches, one per kit area (closing #85/#86; #89 is delivered across the hook-events and setup batches). The issue #92 numbering is the area order, not the landing order: batches 3 and 4 may land before batch 1, batch 2 lands once its owner decision is made, and batch 5 lands last and ships the release. Each PR merges only with its batch's exit conditions met (6.3) and its old/new evidence attached. Nothing installs differently on user machines until the last PR ships a release; earlier batches only change internals, so "rollout" to users is the release containing batch 5 plus the documented re-run of `agent-presence setup`.

### 4.2 Rollback

- Code: revert PRs newest-first; every batch leaves the previous behavior one revert away. Batches 1-4 change no installed artifacts, so a revert needs no user action; batch 5's revert additionally requires users to re-run the old version's `setup` (next bullet).
- Harness downgrade order (kit adoption doc, "Verification and rollback") — never downgrade by deleting the ledger:
  1. run the new version's `agent-presence uninstall`;
  2. inspect its report for anything `kept`;
  3. run the new version's `verify` and `doctor` until both report no new and no legacy duplicates;
  4. install the old version and run the old `agent-presence setup`.
     Acceptance exercises exactly this: after new-install → new-uninstall → old-setup, the old hooks fire exactly once per event (S12).
- Data: no `PresenceState` format change to roll back — scans are stateless and `usageSnapshots` keep their shape (3.2); the kit ledger is additive and ignored by old versions.
